# Phase 1 data model: insights snapshots and poll state

**Feature**: 079-insights-core-bluesky | **Spec**: [spec.md](./spec.md) | **Research**: [research.md](./research.md)

Four new project-owned tables in a new schema module `src/server/db/schema/insights.ts`, one
migration (`drizzle/0041_*.sql`, generated by `pnpm db:generate` — never hand-written), **no new
enum**, **no new activity or notification label**, **no change to any existing table**.

Every table carries `project_id` referencing `projects.id` with `ON DELETE CASCADE` (constitution
III, FR-022) and is reachable only through the scoped DAL.

---

## §1 `post_metric_snapshots` — one reading of one target's numbers (FR-014)

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | `gen_random_uuid()` |
| `project_id` | `uuid` NOT NULL | → `projects.id` `ON DELETE CASCADE` |
| `post_target_id` | `uuid` NOT NULL | → `post_targets.id` `ON DELETE CASCADE` |
| `social_account_id` | `uuid` NOT NULL | → `social_accounts.id` `ON DELETE CASCADE`. Denormalised from the target for the allowance window count (research §4, §7) |
| `provider_key` | `text` NOT NULL | the platform whose words these are; never used to branch in shared code |
| `captured_at` | `timestamptz` NOT NULL | the moment of the read; the panel's "as of" |
| `metrics` | `jsonb` NOT NULL default `{}` | only keys the provider declared **and** the platform returned (FR-018) |
| `created_at` | `timestamptz` NOT NULL | `defaultNow()`. There is deliberately **no `updated_at`**: the row is never updated |

Constraints:

| Name | Rule | Requirement |
|---|---|---|
| `post_metric_snapshots_subject_uq` | `UNIQUE (project_id, post_target_id, captured_at)` | FR-017 — a repeat capture at the same instant is `ON CONFLICT DO NOTHING` |
| `post_metric_snapshots_captured_at_ms` | `captured_at = date_trunc('milliseconds', captured_at)` | research §8 |
| `post_metric_snapshots_metrics_size` | `octet_length(metrics::text) <= 2000` | FR-014, after `engagement_items_provider_data_size` |
| `post_metric_snapshots_metrics_object` | `jsonb_typeof(metrics) = 'object'` | the panel iterates declared keys over an object |
| `post_metric_snapshots_provider_key_len` | `char_length(provider_key) BETWEEN 1 AND 50` | — |

Indexes:

| Name | Columns | Serves |
|---|---|---|
| `post_metric_snapshots_latest_idx` | `(project_id, post_target_id, captured_at DESC)` | read-latest for the panel; also the unique constraint's lookups |
| `post_metric_snapshots_window_idx` | `(social_account_id, captured_at)` | the allowance window `COUNT(*)` (research §4) |
| `post_metric_snapshots_captured_idx` | `(captured_at)` | retention pruning (§11) |

**Append-only is a property of the DAL, not a trigger** (FR-016, after `EngagementItemsRepo`'s
comment): `PostMetricSnapshotsRepo` exposes `insertIfAbsent`, `latestForTargets` and
`countForAccountSince` and nothing else. There is no `update`, and no single-row `delete`; deletion
happens only through retention pruning (a cross-project module function, §11) and through cascade.

## §3 `post_metric_poll_states` — one row per eligible published target (FR-019)

Primary key is `post_target_id` — one state per target, like `engagement_account_states`' one state
per account.

| Column | Type | Notes |
|---|---|---|
| `post_target_id` | `uuid` PK | → `post_targets.id` `ON DELETE CASCADE` |
| `project_id` | `uuid` NOT NULL | → `projects.id` cascade |
| `social_account_id` | `uuid` NOT NULL | → `social_accounts.id` cascade; the claim groups by it to batch |
| `next_poll_at` | `timestamptz` NULL | `NULL` = frozen, never claimed again (FR-027) |
| `poll_lease_until` | `timestamptz` NULL | lease pair, as `engagement_account_states` |
| `poll_lease_owner` | `uuid` NULL | |
| `last_polled_at` | `timestamptz` NULL | a read was attempted |
| `last_captured_at` | `timestamptz` NULL | a read succeeded and a snapshot exists; the schedule's input |
| `consecutive_failures` | `smallint` NOT NULL default 0 | |
| `last_error` | `text` NULL | always `redact()`ed before it is written (FR-041) |
| `failing_since` | `timestamptz` NULL | set when `consecutive_failures` goes 0 → 1, cleared on success; the panel's "reads have been failing since" (FR-066) |
| `frozen_at` | `timestamptz` NULL | |
| `frozen_reason` | `text` NULL | one of `settled`, `gone` |
| `created_at`, `updated_at` | `timestamptz` NOT NULL | `$onUpdate` as elsewhere |

Constraints:

| Name | Rule | Requirement |
|---|---|---|
| `post_metric_poll_states_lease_pair` | `(poll_lease_until IS NULL) = (poll_lease_owner IS NULL)` | FR-019 |
| `post_metric_poll_states_failures_nonneg` | `consecutive_failures >= 0` | FR-019 |
| `post_metric_poll_states_frozen_pair` | `(frozen_at IS NULL) = (frozen_reason IS NULL)` | — |
| `post_metric_poll_states_frozen_reason_enum` | `frozen_reason IS NULL OR frozen_reason IN ('settled','gone')` | a text CHECK, not a pg enum: no enum means no `ALTER TYPE` in a later entry, and 077's partial-index/enum trap (`docs/decisions.md`) is avoided entirely |
| `post_metric_poll_states_frozen_has_no_next` | `frozen_at IS NULL OR next_poll_at IS NULL` | FR-027 — a frozen row cannot also be due |
| `post_metric_poll_states_failing_pair` | `(consecutive_failures = 0) = (failing_since IS NULL)` | FR-066's line is derived from one column, not inferred |
| `post_metric_poll_states_last_error_len` | `last_error IS NULL OR char_length(last_error) <= 500` | — |

Index:

| Name | Columns | Predicate | Serves |
|---|---|---|---|
| `post_metric_poll_states_claim_idx` | `(next_poll_at, post_target_id)` | `WHERE poll_lease_until IS NULL AND next_poll_at IS NOT NULL` | oldest-due-first claim (FR-034) |

**Freeze is terminal and expressed in two places at once**: `next_poll_at = NULL` *and*
`frozen_at`/`frozen_reason` set. The CHECK above makes the inconsistent pair unstorable, and the
claim predicate requires `next_poll_at IS NOT NULL`, so a frozen row is invisible to the claim
regardless of what any future caller forgets.

## §4 `account_metric_poll_states` — one row per eligible account (FR-020)

`engagement_account_states`' shape minus `cursor`, `provider_state`, `backfilling` and `gap_at`.

| Column | Type | Notes |
|---|---|---|
| `social_account_id` | `uuid` PK | → `social_accounts.id` cascade |
| `project_id` | `uuid` NOT NULL | → `projects.id` cascade |
| `next_poll_at` | `timestamptz` NULL | NULL only transiently while a lease is held; an account never freezes (FR-029) |
| `poll_lease_until`, `poll_lease_owner` | | lease pair |
| `last_polled_at`, `last_captured_at` | `timestamptz` NULL | |
| `consecutive_failures` | `smallint` NOT NULL default 0 | |
| `last_error` | `text` NULL | redacted |
| `failing_since` | `timestamptz` NULL | |
| `created_at`, `updated_at` | | |

Constraints: `account_metric_poll_states_lease_pair`, `..._failures_nonneg`, `..._failing_pair`,
`..._last_error_len` — the same rules under their own names. There is **no** frozen pair: an account
is never frozen.

Index: `account_metric_poll_states_claim_idx (next_poll_at, social_account_id)
WHERE poll_lease_until IS NULL AND next_poll_at IS NOT NULL`.

## §5 Lazy row creation (FR-020)

Neither poll-state table is populated by a migration. Rows are created inside the claim, in the same
transaction as the claim, exactly as `claimDueEngagementReads` does
(`src/server/dal/engagement-read-claims.ts:38-55`):

- **Account states**: for every `social_accounts` row that is `removedAt IS NULL`, `status =
  'active'`, has `provider_key` in the set of providers that declare `insights` and are *not*
  `unavailable`, and has no state row — insert `{ socialAccountId, projectId }` with
  `onConflictDoNothing`. `next_poll_at` defaults to `now()` so a new account is due at once.
- **Post states**: for every `post_targets` row that is `status = 'published'`,
  `external_id IS NOT NULL`, `published_at IS NOT NULL`, whose account is active and on such a
  provider, and has no state row — insert with `next_poll_at = nextPostPollAt({ publishedAt,
  lastCapturedAt: null, now, minIntervalMs })`, which is `publishedAt + 1 h` for a fresh target and
  `now` for one already past the 28-day boundary (FR-026). The creation query is **bounded by
  `INSIGHTS_TARGETS_PER_RUN`** so a large archive drains over ticks instead of arriving as one spike
  (the spec's one-off-capture decision).

An install whose providers all omit `insights` matches nothing and gains no rows (SC-010).

A target published by hand with no external id is excluded by the `external_id IS NOT NULL`
predicate, so it never gets a state row at all — which is how FR-039 is satisfied without a skip
path that could increment a failure count. The section's `skippedNoExternalId` count comes from the
*creation* query's companion count (targets that are `published` with `resolved_at IS NOT NULL` and
`external_id IS NULL` on an insights provider), not from a claim.

## §6 The two state machines

**A target's poll state**

```text
            (lazily created)
                  │  next_poll_at = publishedAt + 1h, or now if age >= 28d
                  ▼
            ┌───────────┐  claim (lease)   ┌──────────┐
            │    due    ├─────────────────►│  leased  │
            └───────────┘                  └────┬─────┘
                  ▲                             │
   next_poll_at ← │  snapshot inserted,         │ page/metrics
   nextPostPollAt │  failures=0, failing_since=NULL
                  │                             │
                  ├── retryable/fatal: failures+1, next_poll_at = nextRetryAt(...)
                  ├── rate_limited:    next_poll_at = retryAt ?? nextRetryAt, failures unchanged
                  ├── credentials_invalid: markInvalidEmitting, failures+1, lease released
                  ├── unavailable:     lease released, nothing else changed
                  └── allowance refusal: lease released, next_poll_at unchanged (still due)
                  │
                  ▼ nextPostPollAt returns null  ──or──  page entry kind = "gone"
            ┌──────────────────────────────────────────┐
            │ frozen: next_poll_at NULL,               │  terminal. Never claimed again.
            │ frozen_reason 'settled' | 'gone'         │  Existing snapshots are kept.
            └──────────────────────────────────────────┘
```

A `gone` freeze leaves `consecutive_failures` at 0 and writes no `last_error` (FR-042): it is not a
failure.

**An account's poll state**: the same minus the frozen state. A success sets
`next_poll_at = nextAccountPollAt(...)`, never `NULL`.

## §7 The DAL (`src/server/dal/insights.ts`, `src/server/dal/insights-claims.ts`)

Registered in `createSchedulingRepos` (the tick) and in `buildScope` (the UI) in
`src/server/dal/scope.ts`, beside the four engagement repos.

```ts
interface PostMetricSnapshotsRepo {
  /** ON CONFLICT DO NOTHING on (project_id, post_target_id, captured_at). FR-017. */
  insertIfAbsent(input: NewPostMetricSnapshot): Promise<{ id: string; inserted: boolean }>;
  /** The newest snapshot per target, for the panel. One query for a post's whole target list. */
  latestForTargets(postTargetIds: readonly string[]): Promise<Map<string, PostMetricSnapshotRow>>;
  /** COUNT(*) for the allowance window (research §4). */
  countForAccountSince(socialAccountId: string, since: Date): Promise<number>;
}

interface AccountMetricSnapshotsRepo {
  insertIfAbsent(input: NewAccountMetricSnapshot): Promise<{ id: string; inserted: boolean }>;
  latestForAccounts(socialAccountIds: readonly string[]): Promise<Map<string, AccountMetricSnapshotRow>>;
  countForAccountSince(socialAccountId: string, since: Date): Promise<number>;
}

interface PostMetricPollStatesRepo {
  get(postTargetId: string): Promise<PostMetricPollStateRow | null>;
  /** For the panel: one query for a post's whole target list. */
  getMany(postTargetIds: readonly string[]): Promise<Map<string, PostMetricPollStateRow>>;
  /** `expectedLeaseOwner` conditions the write on the lease still being ours (077's stale-result guard). */
  update(postTargetId: string, patch: PostPollStatePatch, expectedLeaseOwner?: string): Promise<void>;
  /** Account removal: a soft delete does not cascade, so this is explicit (as EngagementAccountStatesRepo). */
  deleteForAccount(socialAccountId: string): Promise<void>;
}

interface AccountMetricPollStatesRepo { /* get, update, deleteForAccount — same shapes */ }
```

Neither snapshots repo has `update` or `delete`. Pruning is two module-level functions —
`prunePostMetricSnapshotsBefore(before, limit)` and `pruneAccountMetricSnapshotsBefore(before,
limit)` — wrapped in `crossProject(...)` by the caller, exactly as `pruneEngagementItemsBefore` is.

**The claim** (`src/server/dal/insights-claims.ts`), two functions mirroring
`claimDueEngagementReads`:

```ts
claimDueAccountMetricPolls(opts: { now, limit, leaseMs, minIntervalMs, providerKeys }): Promise<ClaimedAccountMetricPoll[]>
claimDuePostMetricPolls(opts:    { now, limit, leaseMs, minIntervalMs, providerKeys }): Promise<ClaimedPostMetricPoll[]>
```

Both run in `crossProject`, create missing state rows first (§5), then
`SELECT ... FOR UPDATE OF <the poll-state table> SKIP LOCKED` ordered by `(next_poll_at, id)` with
`LIMIT`, and stamp the lease (FR-032, FR-034). `FOR UPDATE` names **only** the poll-state table, so
a concurrent publish holding the `post_targets` or `social_accounts` row never blocks a claim
(FR-032, SC-008). `ClaimedPostMetricPoll` carries the state row plus the target's `externalId`,
`publishedAt`, `socialAccountId` and `projectId` and the stripped account row — everything the
provider call needs, so nothing is re-read inside the per-account transaction.

## §8 How the panel reads this (FR-062 … FR-066)

`getPostView` (`src/server/services/posts/view.ts`) gains one field per target:

```ts
interface PostViewTarget {
  /* …unchanged… */
  /** Pure data for the performance panel; never a number the UI has to interpret. */
  insights: TargetInsightsView;
}

type TargetInsightsView =
  | { state: "not_published" }
  | { state: "no_external_id" }                                        // published by hand
  | { state: "platform_unsupported"; providerName: string }            // provider omits `insights`
  | { state: "unavailable"; reason: string; docsPath?: string }
  | { state: "not_polled_yet"; firstReadDueAt: Date | null }
  | { state: "nothing_reported"; capturedAt: Date }
  | { state: "reported"; capturedAt: Date; rows: { label: string; value: number }[] }
  | { state: "gone"; snapshot: { capturedAt: Date; rows: { label: string; value: number }[] } | null }
  | { state: "failing"; since: Date; reason: string;
      snapshot: { capturedAt: Date; rows: { label: string; value: number }[] } | null };
```

Nine shapes cover the eight honest states FR-065 enumerates plus `not_published`. Two of them carry
the last good snapshot alongside the notice, which is FR-066 (`failing`) and the spec's US1-AS7
(`gone`). `rows` is built by walking the provider's **declared** key list in declaration order and
emitting only the keys present in the snapshot, each with the provider's own `label` — so FR-064 is
a property of the builder and the component has no absence logic at all, and FR-067's "no chart, no
delta" is true because the view type carries no second snapshot to compare against.

The builder is a pure function in `src/lib/insights/panel.ts`, taking the declaration, the latest
snapshot and the poll state, and reading no clock and no database. Its eight-state table is the
single place state is decided, which is what SC-004 tests against.

## §9 Project isolation

| Table | `project_id` | Reached through | Cascades from |
|---|---|---|---|
| `post_metric_snapshots` | NOT NULL | `PostMetricSnapshotsRepo` (scoped) | project, post → target, account |
| `account_metric_snapshots` | NOT NULL | `AccountMetricSnapshotsRepo` (scoped) | project, account |
| `post_metric_poll_states` | NOT NULL | `PostMetricPollStatesRepo` (scoped) | project, post → target, account |
| `account_metric_poll_states` | NOT NULL | `AccountMetricPollStatesRepo` (scoped) | project, account |

The two claim functions and the two prune functions are the only cross-project readers, each wrapped
in `crossProject(reason, …)` with a reason string, as every other scheduler claim is. The soft
delete of an account does **not** cascade (`removed_at`), so account removal calls
`deleteForAccount` on both poll-state repos — the snapshots are deliberately left, so the panel can
still show what was read while the account was connected (the spec's edge case).

## §10 Configuration (FR-071, FR-072)

Added to `src/server/env.ts` beside the `ENGAGEMENT_*` block, to the `EnvLike` pick and
`schedulerConfig()` in `src/server/scheduler/config.ts`, to a new `INSIGHTS_DEFAULTS` table with an
`insightsConfig(config)` reader, and documented in `.env.example`.

| Variable | Range | Default | Why that default |
|---|---|---|---|
| `INSIGHTS_READ_PAGE_SIZE` | int 1–100 | 25 | the batch size, capped per call at `min(this, provider.insights.maxPostsPerRead)` |
| `INSIGHTS_TARGETS_PER_RUN` | int 1–500 | 50 | two `getPosts` calls per account per tick at the default page size; drains a backlog in minutes, not ticks |
| `INSIGHTS_ACCOUNTS_PER_RUN` | int 1–100 | 20 | `ACCOUNTS_PER_RUN` in `engagement-read.ts` is 20 |
| `INSIGHTS_POLL_MIN_INTERVAL_SECONDS` | int 60–86400 | 900 | the floor no cadence can cross (FR-028); 15 min is well inside the hourly band |
| `INSIGHTS_ACCOUNT_POLL_INTERVAL_SECONDS` | int 300–604800 | 21600 | four account reads a day; followers do not need an hourly figure |
| `INSIGHTS_TIME_SHARE` | float 0–1 | 0.3 | research §6 — below engagement's 0.8 because insights is the least urgent section |
| `INSIGHTS_READ_RESERVE` | float 0–1 | 0.5 | FR-047 — half of each account's allowance is untouchable by polling, double engagement's 0.25 for writes |
| `INSIGHTS_RETENTION_DAYS` | int 1–3650 | 400 | research §11 |
| `INSIGHTS_PRUNE_BATCH` | int 1–1000 | 200 | `ENGAGEMENT_DEFAULTS.pruneBatch` |

At the defaults, an account with 50 live targets spends 2 `getPosts` + 1 `getProfile` ≈ 3 calls a
tick against a declared 1,666/hour budget whose reserve floor is 833 — so the reserve never binds
under ordinary load (FR-072), and `tests/lint/env-coverage.test.ts` keeps all nine documented.

## §11 Retention (FR-073, FR-074)

`src/server/services/insights/retention.ts`, after `services/engagement/retention.ts`:

```ts
prunePostMetricSnapshots(config, now): Promise<number>      // captured_at < now - retentionDays
pruneAccountMetricSnapshots(config, now): Promise<number>
```

Both are called from `runHousekeeping`, each adding its own key to `HousekeepingCounts`
(`postMetricSnapshotsPruned`, `accountMetricSnapshotsPruned`), each one bounded batch of
`INSIGHTS_PRUNE_BATCH` per tick. Neither touches a poll state, a target, a post or an account
(FR-074): the `DELETE` names only the snapshot table, and a frozen target's state row survives its
last snapshot being pruned.
