# Data model: a project's brand identity

**Feature**: `specs/069-brand-profile-fields` | **Date**: 2026-10-13

Phase 1. Three columns, one enum value, one migration. No new table, no new index, no new foreign key.

## 1. `projects` — three optional brand values

`src/server/db/schema/projects.ts`, added after `defaultVoiceProfileId` so the generated migration is a
clean `ADD COLUMN` sequence:

| Column | Type | Null | Default | Meaning |
|---|---|---|---|---|
| `tagline` | `text` | yes | none | The one-sentence description. Single line (P8). ≤ 200 characters. |
| `description` | `text` | yes | none | The longer explanation. Paragraph breaks preserved (P9). ≤ 1000 characters. |
| `website_url` | `text` | yes | none | One absolute `http`/`https` link, stored as typed apart from trimming (B6). ≤ 500 characters. |

Drizzle fields: `tagline`, `description`, `websiteUrl`. `ProjectRow`/`ProjectRecord` gain
`string | null` for each.

**No length CHECK, no default, no index** (P1). The limits are Zod rules at the boundary, like `name`
(80) and `slug` (48) on this same table; nothing queries, sorts or filters by these columns.

### Invariants

1. **Empty is `NULL`, never `''`** (B3, FR-007). The schema never writes an empty string: the brand
   schemas map a value that normalises to empty onto `null`. There is therefore exactly one empty state
   for the prompt, the form and the audit log to reason about. A `''` in these columns would be a defect,
   and the validation tests assert the mapping.
2. **Not versioned** (B2, FR). No history table, no `voice_profile_versions` analogue, and no post
   records which tagline produced it. The current value is the answer to "what is this product?".
3. **Independently present or absent.** All eight combinations are legal states; none implies another.
4. **Every existing row ends with three `NULL`s** (FR-003, SC-003), because the migration adds columns
   without a default and performs no data step.
5. **Project-owned, already registered.** `project-owned.ts` carries `{ table: "projects", scopeColumn:
   "id" }`, so the scope-check harness fails any statement that reads these columns without a project
   pin. Nothing to register.

### Lifecycle

```text
NULL ──save non-empty──▶ value ──save different non-empty──▶ value'
 ▲                        │
 └──save empty/whitespace─┘      (each arrow writes exactly one audit row)

omitted from the submission ──▶ no transition, no audit row   (FR-008)
same normalised value       ──▶ no transition, no audit row   (FR-016)
refused value               ──▶ no transition at all, for any of the three (FR-010)
```

Created by `createProject`? No — project creation does not take brand values (P11), so a new project
begins at `NULL, NULL, NULL`. Deleted? Nothing in `src/server` deletes a project; the columns live and
die with the row.

## 2. `membership_action` — one new value

`src/server/db/schema/audit.ts`, appended to the `pgEnum` after `llm_credential_update`:

```text
project_brand_update
```

One value for all three fields (B11, P14). A row:

| Column | Value |
|---|---|
| `project_id` | the project, supplied by `createAuditRepo(exec, projectId)` |
| `actor_user_id` | the owner or admin who saved, `null` if unknown |
| `action` | `project_brand_update` |
| `subject_user_id`, `subject_email` | `null` — the subject is a field, not a person |
| `details` | `{ field, previous, next }` |
| `created_at` | `now()` |

`details.field` is `"tagline" | "description" | "websiteUrl"`; `previous` and `next` are
`string | null`, holding the stored values. **No key named `url`** — `assertAuditDetailsSafe` refuses any
details key matching `/token|url|password|secret/i`, so the website's link travels in `previous`/`next`
and its identity in `field` (B12's caveat, asserted by a test rather than remembered).

Append-only, as the whole table is: the DAL exposes `insert` and `list` only. Readable by members with
`audit: ["view"]` (owner, admin) — no new read surface, and no public API operation reads this table
(FR-019).

## 3. Migration `0026`

Generated by `pnpm db:generate`, reviewed by hand, committed with the schema change; `pnpm db:check` must
report no drift.

```sql
ALTER TYPE "public"."membership_action" ADD VALUE 'project_brand_update';--> statement-breakpoint
ALTER TABLE "projects" ADD COLUMN "tagline" text;--> statement-breakpoint
ALTER TABLE "projects" ADD COLUMN "description" text;--> statement-breakpoint
ALTER TABLE "projects" ADD COLUMN "website_url" text;
```

(The exact file name is whatever `drizzle-kit` chooses, `0026_*.sql`, plus its `meta/` snapshot and
journal entry.)

**Why this is safe on a live install** (P4):

- Purely additive DDL. No `UPDATE`, no `ALTER COLUMN`, no `NOT NULL`, no default — so no table rewrite
  and no lock held while rows are touched.
- The new enum label is **added and not used** in this migration. Postgres forbids using a label
  committed in the same transaction; nothing here inserts an audit row, so the restriction never
  applies. `0025` and `0008` ship the same shape.
- Applies identically to an empty database and to one with existing projects. Afterwards every project
  has three empty brand values, so every project's composed prompt is byte-identical to before
  (FR-003 → SC-003), and the golden fixture is the regression test for it.
- No operator step, no backfill, no feature flag, nothing to turn on.
