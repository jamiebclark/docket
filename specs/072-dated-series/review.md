## Verdict

The architecture is right and the hard parts are right. The parser really was extended rather than
duplicated (`csv.test.ts` is byte-identical and green, which is the proof FR-020 asked for); the
date rules are one pure module reusing `periodStartInstant`, so DST disambiguation has a single
implementation; `unique(row_id, year)` genuinely makes "a row fires at most once a year" a database
fact rather than a read-then-write; the queue floor lives on the post, so US4 holds on the review
path as well as the worker path; and cadence semantics are untouched, which the parity suite and the
whole pre-existing standing-series suite confirm. But three defects reach production behaviour, and
all three sit on cross-pass seams rather than inside one file. The series detail screen **throws**
for any list containing a year-specific row — a data shape pass 5's read model and pass 6's page
disagree about. A dated run that does not finish inside one tick is **closed, with its remaining
positions abandoned**, whenever lead time is non-zero: the T059 resume fix was written against pass
7's lead-0 tests and contradicts pass 6's lead-time design. And the per-date cap buckets every-year
and year-specific rows separately, so a list that imports cleanly can make the run-open insert
violate `requested_count BETWEEN 1 AND 10` — the exact collision FR-013 and research § 3 were
written to prevent. A fourth, the empty `firedYears` passed when a row's date is edited, aborts a
whole date's run on a unique violation. Fix those four and this is mergeable; the four minors are
cosmetic or observability and can follow.

- [ ] 🛑 BLOCKER F2 — with a lead time, a dated run that spans ticks is closed as stale and its unfinished positions are dropped
      where:  src/server/services/standing-series/run.ts:221, src/server/services/standing-series/run.ts:47, src/server/services/standing-series/runner.ts:200
      why:    `openOrResumeDatedRun` resumes an open run only when
              `open.periodStart === today.toString()`. A dated run's `period_start` is the **target
              date**, but with `lead_days = N` the run opens on `target - N` — so on every day of
              the lead window except the target date itself that comparison is false. The run is
              handed to `closeStale` → `closeRun`, which (because `today < periodStart`) does not
              even mark the leftovers `missed`: they stay `queued` on a closed run, permanently.
              `evaluateDatedSeries` has already advanced those rows to next year, so
              `evaluation.dueDate` is `null` and no replacement run opens; the claim predicate then
              goes false on all three branches (`next_run_at` is NULL for a dated series, no open
              run, no due row), so the series is never looked at again for that date. Concretely:
              `lead_days = 3`, three rows on 14 March, the shipped `STANDING_SERIES_TICK_MAX_POSTS`
              of 2 — the tick on 11 March produces two posts and leaves one position `queued`, and
              the next tick closes the run, so that row produces nothing, this year or ever. It also
              bites a **single** row whenever a position takes a temporary error: `nextDue` returns
              `null` during retry backoff, `hasOpenWork` is true so the producer correctly returns
              with the run still open, and the next tick closes it instead of retrying. Each such
              run closes `incomplete` with `produced = 0`, so three dates in a row also trip the
              self-pause rule. All six lead-time cases use one row and `standingSeriesMaxPosts: 5`,
              and every idempotency and resume case uses `leadDays: 0`, so the suite never reaches
              the state.
      owed:   resume on the run's own identity rather than on a date that only coincides with
              `period_start` when the lead time is zero — e.g. resume any open `period = 'date'` run
              whose `period_start` is still inside its own window
              (`period_start - lead_days <= today <= period_start`), and treat it as stale only once
              `today > period_start`. Add a case with `leadDays > 0` and more positions than
              `maxPosts`, and one where a lead-time position retries, each asserting every row still
              produces exactly one post.
      traces: FR-037, FR-040, US4 AS1, US5 AS2, US5 AS3, SC-003, SC-007, contracts/worker.md § 7

- [ ] 🛑 BLOCKER F3 — the per-date cap counts every-year and year-specific rows separately, so an importable list makes the run insert violate `requested_count BETWEEN 1 AND 10`
      where:  src/server/services/standing-series/dated-import.ts:226, src/server/services/standing-series/dated-rows.ts:49, src/server/services/standing-series/dated-rows.ts:97, src/server/services/standing-series/run.ts:276, src/server/db/schema/standing-series.ts:216
      why:    FR-013 and A11 are explicit that the cap counts "every-year and year-specific rows
              together, so `03-14` and `2027-03-14` both count toward the 14th of March 2027", and
              research § 3 records the plan's resolution of exactly this question (count a
              year-specific row against its own year, and an every-year row against each of the next
              two years). The importer instead counts into a key of month, day and
              `spec.year ?? "any"`, and the row editor filters on
              `(r.year ?? null) === value.spec.year` — so the two kinds never share a bucket, and nor
              do `02-29` and `02-28`, which the leap-day rule (A24) collapses onto the same day in
              three years out of four. A file with ten `03-14` rows plus one `2027-03-14` row
              therefore imports clean, and in 2027 eleven rows carry
              `next_target_date = 2027-03-14`. `openOrResumeDatedRun` sets
              `requestedCount: rows.length` from an unbounded `dueOn`, so the insert violates the
              pre-existing `standing_series_runs_requested_count_range` CHECK. That is a `23514`,
              not a `23505`, so `isUniqueViolation` is false and the error escapes
              `processClaimedSeries` into the section's `.catch` as a `staleResults` tick after tick
              until the window shuts: no run opens and **none** of the eleven rows produces a post.
              Ten `02-28` rows plus one `02-29` row is the same failure with no year-specific row
              involved at all. `import.test.ts`'s eleventh-row case uses eleven identical every-year
              dates, which the current bucketing does catch.
      owed:   count the cap against resolved calendar dates — the row's own year for a year-specific
              row, each of the next two years for an every-year row, per research § 3 — applying the
              leap-day collapse, in the importer and in `addDatedRow`/`updateDatedRow` alike; and
              make `openOrResumeDatedRun` defensive about `rows.length > DATED_ROWS_PER_DATE_MAX`
              instead of letting a CHECK violation escape. Add cases for `03-14` plus `2027-03-14`
              and for `02-28` plus `02-29`.
      traces: FR-013, A11, A24, research.md § 3

- [ ] MAJOR F4 — a row's date edited forward inside a year it has already fired or missed re-arms, then aborts that whole date's run on `unique(row_id, year)`
      where:  src/server/services/standing-series/dated-rows.ts:112, src/server/services/standing-series/dated-import.ts:318, src/server/services/standing-series/run.ts:288, src/server/services/standing-series/run.ts:295
      why:    `updateDatedRow` recomputes `next_target_date` as
              `nextTargetDate(value.spec, today, [])` — an **empty** fired-years list — even though
              contracts/services.md § 7 says the edit "recomputes `next_target_date` from today and
              **deletes no occurrence** (the row's past firings stay)". With 2026's occurrence
              already present (produced on 14 March, or recorded `missed` because the series was
              paused across it), editing the date to 1 June resets `next_target_date` to
              `2026-06-01`. On 1 June the run-open transaction inserts an occurrence for
              `(row, 2026)`, hits the unique index and rolls back; the recovery path re-reads
              `openFor`, finds nothing — the run rolled back too — and rethrows. Because run-open is
              one transaction for the whole date, **every other row due on 1 June loses its post as
              well**, and the throw repeats each tick until the window closes. `importDatedList`
              carries the same `[]` on its `existing.nextTargetDate === null` refresh path, where it

              again, is swept as `missed` on the next pass (inflating the `missed` return even though
              `recordMissed` no-ops against the existing row), and then settles — nothing fires
              twice, but the row shows a stale date in between. `rows.test.ts`'s edit case changes
              the date on a row that has never fired.
      owed:   pass the row's actual fired years (`datedRows.firedYears`) into `nextTargetDate` at
              both call sites — the function already takes them, and `evaluateDatedSeries` and
              `openOrResumeDatedRun` already supply them — and make the run-open path treat an
              occurrence that already exists for a row as "nothing to do for this row" rather than
              failing the whole transaction. Add a case that edits a row's date after it has fired

      traces: FR-028, FR-040, A22, contracts/services.md § 7
