## Code facts

- **F1 — The provider contract.** `src/providers/types.ts`. `validate(content, caps)` sees only `PostContent` (`text`, `media`, `postType`). It cannot see per-target values, live account details or consent. `StepContent` has `text`, `mediaCount`, `videoCount`, `kinds`, `postType`. `PublishContext` has `target.attempt` (attempt count + 1, reset to 1 by every `continue`), `content`, `state`, `now` (DB clock) and `signal`.
- **F2 — G19 is the precedent for a per-target value.** `post_targets.chosen_post_type` (migration `0012`) is stored per target. It is read by `loadTargetContent` (`src/server/services/posts/validate.ts`) for the gate. The composer check (`checkComposition`, `src/server/services/posts/compose.ts`) and `execute()` (`src/server/scheduler/publishing.ts`) read it too. The composer renders a "Post as" fieldset from `TargetCheck.postTypeChoice`, with no provider code. G19 added a column, a check constraint, a field on `postTargetInputSchema` and a `TargetCheck` member. TikTok's three hooks follow the same shape.
- **F3 — One validation path.** `validateTargetContent` → `adaptedMediaFor` → `validateResolvedContent(provider, content)` → `provider.validate`. It serves the composer check (`preview: true`), the gate (`gate()` in `posts/gate.ts`, used by queue, schedule, publish now, approval and retry) and `updatePost`'s "a scheduled target must stay publishable" re-gate. The engine calls `validateResolvedContent` directly, on a target's first step only (`stepState === null`), before reading credentials. A refusal there fails the target on step `engine-validate` with "Can't publish to <platform>: <message>".
- **F4 — The composer saves before it schedules.** `openQueue`, `openScheduleAt` and `openPublishNow` in `Composer.tsx` call `save()` (`saveDraftAction` → `createDraft` / `updatePost`) first. The dialog then calls the service, which runs `gate()` on the saved rows. Anything the person ticks is therefore saved just before any scheduling call, and the gate sees it.
- **F5 — `updatePost` refuses an edit that would break a scheduled target.** After writing, it runs `gate()` on every `scheduled` target and throws `ValidationIssuesError` if any fails. It also refuses any edit once a target is `publishing`, `published` or `ambiguous` (`STARTED`). Media therefore cannot change under an upload in progress.
- **F6 — There is no "duplicate post" feature.** A search of `src/` finds none. A new post gets consent only if a member ticks "I agree" on it, so "a duplicated post does not inherit consent" holds by construction. A test pins it at the service level.
- **F7 — The public API builds its own body.** `createPost` (`src/server/api/operations/posts.ts`) maps `text`, `accountIds`, `overrides`, `mediaIds` and `postTypes` into `createDraft`. Adding optional members to `postTargetInputSchema` does not add them to the API (FR-041). Generator and bulk sources call `createDraft` without them too.
- **F8 — Refresh has one path.** `refreshForPublish` (`src/server/scheduler/credentials.ts`) takes the per-account refresh lease, keyed on the ciphertext the caller saw. A loser gets `changed` (it reuses the stored result) or `busy`. `applyRefreshResult` then writes the outcome: new ciphertext, `needs_reauth` with an emitted event, or a transient hold. The scheduled section (`runTokenRefresh`) uses the same `applyRefreshResult`. It claims accounts whose `credentials_expires_at` is within `TOKEN_REFRESH_WINDOW_HOURS` (default 72).
- **F9 — X's rotating refresh token.** `src/providers/x/refresh.ts` stores both tokens together and keeps the old refresh token when none is returned. The account's `expiresAt` is the refresh token's estimated expiry, never the 2-hour access token's, so the scheduled refresh does not run every tick. `needsRefresh` covers the access token before a publish.
- **F10 — Byte-range reads.** `src/providers/bluesky/media-range.ts` (`readRange`, `storedSize`) reads `bytes=first-last` from the media's public URL. It requires a `206` of exactly that length, and nothing in it is Bluesky-specific.
- **F11 — The engine's timeout race.** `execute()` creates `AbortSignal.timeout(providerTimeoutMs)` and then races `advance` against a `setTimeout` of the same length. If the race is lost, a `mayPublish` step is `ambiguous`. The signal's timer is created first. A fetch that rejects on abort settles through microtasks before the later timer's callback runs. A provider that catches its own abort therefore normally returns first.
- **F12 — G23 and G24.** `afterPublish: true` makes the engine settle `ambiguous` where it would otherwise fail. A provider's own `fatal_error` still fails. `continue.wait` is recorded as `lastError` while waiting.
- **F13 — The engine's 24-hour ceiling.** A target fails "Publishing did not complete." `PUBLISH_MAX_DURATION_HOURS` (default 24) after `first_step_at`. Bluesky's P9 ends its own 24-hour wait at 23 hours for this reason.
- **F14 — The callback query is not passed to `exchangeCode`.** `handleOAuthCallback` (`src/server/services/connect.ts`) passes `code`, `redirectUri`, `state`, `now` and `signal` only. TikTok's granted `scopes` arrive in the callback query (research), so D2 needs them passed.
- **F15 — Account notes have no clock.** `accountNotes({ settings, credentialsExpireAt })` is pure and receives no `now`. D15's "within 30 days" warning needs one.
- **F16 — The requirements summary is capability-only.** `requirementsOf(caps, ctx)` reads static capabilities. The unaudited notes depend on `TIKTOK_APP_AUDITED`, which is read at run time.
- **F17 — Target views.** Target status is shown by `getPostView` (`posts/view.ts`, post detail), `listPosts` (`posts/list.ts`, post list), `CalendarItem` (`services/calendar.ts`) and `TargetCheck` (composer). None of them carries a provider note.
- **F18 — Providers may not import `src/server/**`** (a lint test). X derives its PKCE verifier with `node:crypto` HMAC keyed by `X_CLIENT_SECRET` (`src/providers/x/pkce.ts`). That is the precedent for provider-side keyed crypto from a provider variable.
- **F19 — Environment.** Provider variables are declared by the connect group (`environment`, G8) and merged at startup, never in `src/server/env.ts`. `parseXEnv` is the model: pure, issues carry names and reasons but never values, and one variable without the other is an issue. Compose reads `.env` through `env_file`.
- **F20 — Docs links.** `docsUrl(page, anchor)` in `src/lib/docs.ts` takes a closed `DocPage` union, so `tiktok-setup` must be added there and to `mkdocs.yml`. `tests/integration/docs/published-docs.test.ts` and the doc-link tests resolve every link.
- **F21 — Tests that loop over registered providers.** `registry.test.ts` (key shape, custom rule name `[a-z0-9-]+`, `count("") === 0`) and `requirements.test.ts` include TikTok automatically. So do `limits-inventory.test.ts` (every declared category needs a row) and `tests/integration/limits/enforcement.test.ts` (generated per category). `requirements.test.ts`'s "unchanged" loop names `mock` and `x` only, so it does not change.
- **F22 — Media per target.** `resolvePublishMedia` returns the planned file for each item: the adapted version's `publicUrl`, its bytes and its facts. TikTok therefore publishes exactly what the planners chose (FR-029) and waits for a version still being built (`notReady` → release).
- **F23 — Composer details read.** `checkComposition` runs outside any transaction, once per debounced edit (200 ms). A live call made there must be cached, or typing spends TikTok's 20-per-minute creator-info budget.

## Plan decisions

### Generic hooks

- **P1 — G25: per-target posting fields (spec D3).** A provider may declare `posting` (`PostingDeclaration`, contracts/generic-hooks.md). It holds the stored values' zod schema and a pure `view({ values, details, postType })`, which returns a list of field views: choice, toggle, text or fixed, each with options, a disabled flag and its reason, and help. The declaration also holds a pure `targetNote(values)` for the status label and a pure `summaryNotes()` for the requirements summary. The composer renders the views; there is no provider UI code. Values are stored in `post_targets.posting_fields` (jsonb, null = never set). They reach `validate` as `PostContent.posting.values` and reach `advance` the same way. Rules such as "Branded content disables Only me" live in `view` and are re-checked in `validate`, so the browser is never trusted. *Why one function, not a declarative rule language:* the rules are few and provider-specific, and a pure function is testable and total. *Reverse:* drop `posting`; the column is ignored.
- **P2 — G26: live account details (spec D4).** A provider may declare `accountDetails.read({ credentials, settings, now, signal })`. It returns non-secret, JSON-safe details validated by the provider's own zod schema, or a plain failure. The server-side service `readAccountDetails(scope, accountId)` (`src/server/services/account-details.ts`) checks `post: ["view"]`, then decrypts the credentials through the pinned scheduling repos (the scope has already resolved membership), as the engine does. If `needsRefresh` says so, it renews them through `refreshForPublish` (F8), so a composer read and a publish cannot both refresh, and a rotated refresh token is written exactly once. It then calls `read` with the provider time limit. An answer is cached in-process for 60 seconds per account. A failure is never cached, so Retry calls again. The cache holds details only, never credentials. *Why in-process:* one web process per install, and a cache miss only costs one creator-info call. *Reverse:* drop the member.
- **P3 — G27: explicit consent per target (spec D5).** A provider may declare `consent: { declaration(values): string }`. Docket then requires an "I agree" per target. The consent is recorded in four columns on `post_targets`: `consent_by_user_id`, `consent_at`, `consent_fingerprint` and `consent_details` (the account details shown, non-secret). The fingerprint is a SHA-256 over canonical JSON (`v: 1`) of the effective text, the post's media ids in order, its video edits, the target's posting values and the details shown (`consentFingerprint`, `src/server/services/posts/consent.ts`). A consent is valid only while the recomputed fingerprint equals the stored one. "Any change clears it" therefore needs no hook on every write path. `updatePost` also nulls a consent that no longer matches, so the view shows the box unticked. *Reverse:* drop `consent`; the columns are ignored.
- **P4 — Consent is recorded on the save before scheduling (F4).** The check response carries each consent target's current `fingerprint`. When the person ticks "I agree", the composer keeps that fingerprint. Every save sends `consent: { fingerprint }` for each ticked target. Before its transaction, the save reads the details through P2 (cache). Inside the transaction it recomputes the fingerprint from the saved content and those details, and records the consent (`scope.membership.userId`, DB clock) only when the two fingerprints are equal. If the content or the details changed in between, nothing is recorded, the next check shows the box unticked, and the gate refuses. Only `member` actors can consent; an API key's `consent` is ignored. *Why at save, not in the schedule dialog:* every schedule path saves first, and the gate then reads the saved row. That path already exists for queue, schedule-at, publish now and approval.
- **P5 — Consent is checked in three places, all through `consentStatus` (one implementation).** (a) The composer check, against the fingerprint sent in the check input: issue `consent_required` "Tick 'I agree' to post to TikTok." (b) The gate, which every scheduling path uses, against the stored consent (same issue). (c) The engine, on a target's first step, after `validateResolvedContent`. There, a missing or stale consent fails with "No consent recorded for this TikTok post; nothing was posted." and no provider call. When `posting_fields` is null (API, generator, bulk), the one issue shown is the provider's `posting_required`, "Open this post in the composer to choose TikTok's settings and agree before scheduling.", and the consent issue is suppressed.
- **P6 — Details at the gate and the engine come from the consent.** `PostContent.posting.details` is the consent's stored details at the gate and in the engine, and the live (cached) details in the composer check. The creator's maximum duration is therefore checked "against the value the person saw when consenting" at the gate (spec FR-009). The live re-check at publish is the provider's own `check_creator` step (D10).
- **P7 — G28: `exchangeCode` receives the callback query.** The input gains `callbackParams: URLSearchParams`, a copy of the callback's query. D2 reads `scopes` from it. It is a fourth generic change beyond the spec's three, but a minimal one: inert for every existing group, recorded in the hooks index and in decisions. *Alternative rejected:* reading `scope` from the token reply, whose field list is UNVERIFIED (research). That reply's `scope` is used only as a fallback when the callback carries none.
- **P8 — G13 input gains an optional `now`.** `notesFor` in `src/server/services/accounts.ts` passes the DB clock. TikTok uses it for "Reconnect TikTok before <date>" within 30 days of the refresh token's (estimated) expiry. Existing providers ignore it.
- **P9 — Summary notes and target notes are part of G25.** `RequirementsSummary` gains an optional `notes?: string[]`, filled from `posting.summaryNotes()` and rendered as a list by `RequirementsSummary.tsx`. Target views (`PostViewTarget`, `PostListItem.targets[]`, `CalendarItem`, `TargetCheck`) gain `note: string | null` from `posting.targetNote(values)`, through one helper `targetNoteFor(providerKey, values)`. *Why optional:* existing literal summaries in tests stay valid.
- **P10 — Schema.** One migration (`0018`) adds five nullable columns to `post_targets`: `posting_fields jsonb`, `consent_by_user_id uuid` (FK `user.id`, on delete set null), `consent_at timestamptz`, `consent_fingerprint text` and `consent_details jsonb`. A check constraint pairs `consent_at` with `consent_fingerprint`. There is no new table and no backfill. Every existing row is null, which means "no fields" and "no consent", and no existing provider reads them. `pnpm db:check` must pass.

### Connect, tokens and configuration

- **P11 — Environment.** `parseTikTokEnv(source)` is modelled on `parseXEnv`. `TIKTOK_CLIENT_KEY` (≤ 200, no whitespace) and `TIKTOK_CLIENT_SECRET` (≤ 500, no whitespace) must come together. `TIKTOK_APP_AUDITED` accepts `true` or `false` (any case), defaults to false, and anything else is an issue. `tiktokAudited()` reads `process.env` each call, so tests use `vi.stubEnv`. Startup issues carry names and reasons, never values.
- **P12 — The reply envelope (UNVERIFIED) is read in one function.** The research says errors may come back as HTTP 200 "with an error code in the body", but not where. `readEnvelope(body)` takes the error code from `body.error.code` when it is a string other than `"ok"`, or from `body.error` when that is a string. The data comes from `body.data` when it is an object, else from `body`. A 2xx without the expected data field is `unreadable`. That is retryable before the publishing request, sends the target to the status checks after the final chunk, and is ambiguous after the photo `init`. Codes are matched exactly against the research's lists. The envelope is an owed live check.
- **P13 — Token reply (UNVERIFIED beyond `open_id` and `refresh_token`).** Required: `access_token`, `refresh_token` and `open_id`, which are strings. `expires_in` defaults to 86,400 and `refresh_expires_in` (if present) sets the refresh token's expiry. Otherwise the expiry is estimated at 365 days from issue, and `refreshExpiryEstimated: true` is stored. `scope` from the reply is the fallback when the callback carries no `scopes`. If neither says what was granted, the exchange continues. The creator-info read right after it then fails with `scope_not_authorized` when `video.publish` is missing, and that also gets D2's refusal.
- **P14 — Identity.** `externalId` = `open_id`. `displayName` = "nickname (@username)", from creator info, falling back to "nickname", then "@username", then the `open_id`. Settings: `{ username?, nickname? }` (lenient, `.strip()`).
- **P15 — Account expiry and refresh timing.** The account's `expiresAt` is the refresh token's (estimated) expiry, as for X (F9). `needsRefresh` is true when the access token expires within 30 minutes. The scheduled refresh renews an idle account within `TOKEN_REFRESH_WINDOW_HOURS` of the refresh token's expiry. The composer read (P2) renews through `needsRefresh` as well. *Why not the 24-hour access expiry:* with a 72-hour window it would be in the window at every tick (F8, F9).
- **P16 — Refresh outcomes.** `invalid_grant`, `invalid_client`, `unauthorized_client`, `invalid_request` and `access_token_invalid` are definitive (`ok: false`, the account needs reconnecting). Client problems point to the two variables. HTTP 5xx, 429, network errors and unreadable replies are transient, with `retryAt` now + 5 minutes. The returned refresh token replaces the stored one whenever it differs. When the reply has none, the old one is kept along with its issue time.
- **P17 — No PKCE and no `disable_auto_auth`.** The research's web parameter list has neither. PKCE on web is an owed live check (FR-037).

### Capabilities and validation

- **P18 — Declaration** (`src/providers/tiktok/capabilities.ts`, values from spec D8).
  - Text: 2,200 under the custom rule `utf16` (unit "UTF-16 units", `count = s.length`).
  - Media: `maxImages` 35, `image/jpeg` and `image/webp` with JPEG as the output, 20,000,000 bytes, `maxWidth` 1080, `maxHeight` 1920, required. No text-only posts. Post types `image`, `carousel`, `video`. No `postTypeChoices`.
  - Video: one, never with images. Containers `mp4` and `mov`. Codecs `h264`, `hevc`, `vp8` and `vp9` (ffprobe names). 23 to 60 fps, 360 to 4,096 px each side, 4,000,000,000 bytes, 300 s. No aspect range, bitrate, audio codec or recommended shape.
  - `defaultPublishLimit` 15 / 86,400 s (approximate).
- **P19 — `validateTikTok`** = `validateAgainstCapabilities` plus TikTok's own issues. The issues are listed in contracts/tiktok-publishing.md §2: posting missing, privacy unchosen, not offered or not private while unaudited, unaudited account without `SELF_ONLY`, branded content set to private, an incomplete disclosure, an interaction the creator disabled, a photo title over 90, a video longer than the creator's maximum, non-`https` photo addresses, and TikTok wording for video plus images and for two videos. Values are re-checked here whatever the browser sent.
- **P20 — Unaudited installs store `SELF_ONLY`.** In an unaudited install `view` returns privacy as `fixed` with value `SELF_ONLY`, and the composer sends that value. A stored privacy other than `SELF_ONLY` there is a blocking issue at the gate. At publish it fails with "This TikTok app is set as not audited, so it can only post privately; nothing was posted." (spec edge case). A target stored as `SELF_ONLY` keeps it after the operator sets the app audited.
- **P21 — Privacy labels.** `PUBLIC_TO_EVERYONE` → "Everyone", `MUTUAL_FOLLOW_FRIENDS` → "Friends (mutual followers)", `FOLLOWER_OF_CREATOR` → "Followers", `SELF_ONLY` → "Only me". An unknown option from creator info is shown as its code and can be chosen, as TikTok offers it.
- **P22 — Declaration text.** "By posting, you agree to TikTok's Music Usage Confirmation." When "Branded content" is ticked it becomes "By posting, you agree to TikTok's Branded Content Policy and Music Usage Confirmation." This is plain text with no links (NEEDS RESEARCH, spec D7). The research gives the same branded text whichever box is ticked, but the audit checklist ties it to branded content. *Decision:* "Your brand" alone keeps the plain text. Recorded as UNVERIFIED in the setup doc.

### Publishing

- **P23 — Steps** (`tiktokStepFor`, pure and total).
  - Video: `check_creator` → `start_upload` → `upload_chunk_1` … `upload_chunk_N` → `check_status`.
  - Photo: `check_creator` → `publish_photos` → `check_status`.
  - Only `upload_chunk_N` (the last) and `publish_photos` have `mayPublish: true`. `check_status` has `afterPublish: true`.
  - A state that fails to parse is handled by its marker. With a `publishId` and `sentAt` marker it routes to `check_status`, whose `advance` returns `ambiguous` ("Docket lost track of this TikTok post's progress; check TikTok before retrying."). Without one it routes to `check_creator` (nothing was published).
- **P24 — Chunk plan** (`chunkPlan(size)`, spec D9). The chunk size is `clamp(floor(size / 30), 5_242_880, 64_000_000)` and the count is `floor(size / chunkSize)`. A file under 5,242,880 bytes, or any file whose count is 1, is sent as one chunk with `chunk_size = video_size`. *Why for a count of 1:* the research says small files "are uploaded whole". A whole-size `chunk_size` satisfies both "≥ 5 MB" (when the file is) and `floor(size/chunk_size) = 1`. Chunk `k` (1-based) covers `[(k-1)·c, k·c − 1]`, except the last, which covers `[(N−1)·c, size − 1]`. The plan is checked before `init`: count 1 to 1,000, and the final chunk under 128,000,000 bytes. SC-006's figures are pinned by tests.
- **P25 — The upload address is sealed in the state.** AES-256-GCM, with a key of HMAC-SHA256(`TIKTOK_CLIENT_SECRET`, "docket:tiktok:upload-url:v1"), a random 12-byte IV, and AAD `<target id>:<publish_id>`. It uses `node:crypto` only, as in F18 (`src/providers/tiktok/sealed.ts`). The address is never logged, summarised or put in an error. A seal that cannot be opened (the secret was rotated, or the state was tampered with) is treated as an expired address: the upload restarts. *Alternatives rejected:* keeping it out of the state (every chunk is a new tick, so it would be lost after every step), and the server's `encryptSecret` (providers may not import `src/server`).
- **P26 — Chunk outcomes** (contracts/tiktok-publishing.md §5).
  - Non-final chunk:
    - `206` moves on.
    - `201` means TikTok considers the upload complete early, so the post may now exist. The state moves to the status checks. It never fails, and never sends again.
    - `403` restarts.
    - Any other 4xx on a repeat restarts (P27); on a first send it fails with nothing posted.
    - 429 waits at least 60 s or `Retry-After`. 5xx, a timeout or a reset is retried.
  - Final chunk:
    - `201` goes to the status checks.
    - `206` (TikTok wants more bytes) fails with nothing posted ("TikTok did not receive the whole video; nothing was published.").
    - `403` restarts (the upload did not complete, so nothing was published).
    - Any other 4xx fails with nothing posted.
    - 429, 5xx, a timeout, a reset or an unreadable reply goes to the status checks. The `publish_id` is known, so a status read is safe and the final chunk is never sent twice.
- **P27 — A repeat is `ctx.target.attempt > 1` on a chunk step.** A `continue` resets the attempt count (F1), so an attempt above 1 on the same chunk means the previous send of that chunk was retried.
- **P28 — The address is renewed ahead of expiry.** Before sending any chunk, an address issued 55 minutes ago or more (`UPLOAD_SAFE_AGE_MS`) restarts the upload with nothing sent. Restarts (any cause) are counted, with at most 2. The third fails with spec D9's message.
- **P29 — The posting-cap wait ends at 23 hours, not 24.**
  - Which refusals wait: `spam_risk_too_many_posts` and `reached_active_user_cap`, at the creator check, at the video `init` or as a refused photo `init`. Nothing is sent.
  - How it waits: `continue` with `wait` (G24), the cap message, and `notBefore` one hour later. `capWaitSince` is kept in the state.
  - When it fails: a refusal at least 23 hours after the first fails with the cap message.
  - *Why against the letter of spec D10's 24 hours:* the engine fails a target 24 hours after its first step (F13), which is at or before the first refusal. A 24-hour rule would never fire, and the person would see "Publishing did not complete." instead of TikTok's reason. This is the same as Bluesky's P9.
- **P30 — Status pace** (spec D11).
  - Reads: the first at least 15 s after `sentAt`, then at least 60 s apart until 10 minutes after it, then at least 300 s apart. Each read is one `continue` with `notBefore` and the wait text "TikTok is processing the post; it may take a few minutes to be visible."
  - The ceiling is 60 minutes after `sentAt`. A read is scheduled at the ceiling itself, so a late `PUBLISH_COMPLETE` is not missed. A non-final status at or after the ceiling is ambiguous.
  - Read failures: `access_token_invalid` is retried with credentials expired. 429, 5xx and network errors are retried. `invalid_publish_id` and `token_not_authorized_for_specified_publish_id` are ambiguous ("TikTok would not report on this post; check TikTok before retrying."). G23 makes every engine-side failure ambiguous.
- **P31 — The final-chunk timeout path relies on F11.** The final chunk's `fetch` uses `ctx.signal`, and the provider catches the abort and returns `continue` to the status checks. If the engine's own timer wins anyway, the step is recorded `ambiguous`, which is the safe side. An integration test drives a hanging final chunk through `runTick` and expects the status checks.
- **P32 — Byte ranges are shared.** `readRange` and `storedSize` move to `src/providers/media-range.ts`. `src/providers/bluesky/media-range.ts` becomes a one-line re-export, so no Bluesky test or behaviour changes. Each chunk reads exactly its range. The stored size must equal `MediaItem.bytes` before `init`; a mismatch restarts once, then fails with "The video file changed while it was being sent; nothing was published.".
- **P33 — Fit.** `fitState(state, content)` restarts from `check_creator` a state before publishing whose file (URL and size) or kind (video or photo) no longer matches the content. A state after publishing never restarts.
- **P34 — Requests.**
  - The video `title` and the photo `description` are the effective text. The photo `title` is the photo title when set.
  - `privacy_level` is `SELF_ONLY` when unaudited, otherwise the stored choice.
  - `disable_comment`, `disable_duet` and `disable_stitch` are the opposite of each toggle; duet and stitch are sent for video only. `brand_organic_toggle` follows "Your brand" and `brand_content_toggle` follows "Branded content", both false when the disclosure is off.
  - Never sent: `video_cover_timestamp_ms`, `is_aigc`, `auto_add_music`.
  - `photo_images` are the planned images' public URLs in post order, with `photo_cover_index` 0.
- **P35 — The creator check compares live with chosen** (spec D10).
  - It reads creator info and compares it with the stored values: the privacy is still in `privacy_level_options` (and is `SELF_ONLY` while unaudited); every interaction turned on is not disabled now; the video, as it will be sent, is not longer than `max_video_post_duration_sec`.
  - The nickname shown goes in `summary.response.nickname`.
  - Any mismatch is a `fatal_error` with nothing sent, using spec D10's words.
  - Banned is fatal. A posting cap waits (P29). An HTTP 200 body with an error code is that error.
- **P36 — Refusals explained** (`explainTikTok(code, message)`, spec D13). Each listed code has a plain sentence, followed by "(TikTok: <code>)". TikTok's message is added after scrubbing: control characters are removed, it is cut to 200 characters, and the step's secrets (tokens, upload address) are replaced. `auth_removed` in a `FAILED` status is a `fatal_error` with `credentialsInvalid: true`. A provider's own fatal fails even after publishing (F12), and the account is flagged for reconnecting.
- **P37 — Rate limits.** At most one TikTok call per step per target, so a step stays within the per-token rates of 6 `init`s, 20 creator reads and 30 status reads per minute. A 429 waits at least 60 s or the `Retry-After`. The composer's creator reads are cached (P2).

## Alternatives considered (summary)

| Question | Chosen | Rejected because |
|---|---|---|
| Where consent is captured | On the save that precedes scheduling, verified by fingerprint | A separate consent dialog in every schedule path duplicates four dialogs; the gate already sees saved rows |
| How "any change clears consent" is enforced | Validity = fingerprint match | Clearing on every write path (text, media, edits, overrides, fields) is easy to miss and untestable as a whole |
| Where creator info is cached | In-process, 60 s, details only | A table adds schema for a value TikTok expires in minutes anyway |
| Upload address storage | Sealed in state (P25) | Out of state loses it every tick; server crypto is off-limits to providers |
| Unaudited enforcement | Store `SELF_ONLY`, re-check at gate and publish | Rewriting the privacy silently at publish would post with settings the person did not see |
| Field rules | A pure `view` function per provider | A declarative rule language for three rules is more code and less testable |
| Granted scopes | Callback query (G28), token `scope` as fallback | Token reply fields are UNVERIFIED |
