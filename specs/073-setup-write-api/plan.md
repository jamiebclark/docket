# Implementation Plan: Public API for project setup — projects, voice profiles, posting instructions and slots

**Branch**: `073-setup-write-api` | **Date**: 2026-10-14 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/073-setup-write-api/spec.md`

## Summary

Add seven write operations to the existing `/api/v1` operation table so the first steps of standing a
brand up — create the project, create and refine its voice profile, set an account's posting
instructions, and book its posting week — can be driven over HTTP instead of through the browser.

Nothing new is invented: each operation is a row in `src/server/api/operations/`, declares its
permission, `idempotent`, `resourceParams` and Zod request/response schemas, and calls exactly one
function in `src/server/services/`. The pipeline (`src/server/api/handle.ts`) already authenticates,
rate-limits, checks the permission, wraps writes in `runIdempotent` and maps service errors.

Five small widenings make that possible, and they are the whole of the risk:

1. `ApiOperation.method` gains `"PATCH"` and `"DELETE"` (the router, `OPTIONS`/`Allow`, the
   method-not-allowed answer and the OpenAPI builder are already method-generic; the route module
   already exports both handlers).
2. `resourceParams` gains `accountId`, `profileId` and `slotId`.
3. One new `api_key_permission` value, `manage_setup`, with its `KEY_GRANTS` entry, its enum
   migration and its checkbox in the key form. No existing key holds it.
4. `projects.create` grows to take the whole project shape (policy defaults and brand fields) and to
   return the created project, so one call writes one project in one transaction. `updateSettings`
   is untouched and the browser's create form keeps working with the subset it sends.
5. `setSlotPaused` grows to return the updated slot, mirroring `moveSlot`, so `PATCH /slots/{slotId}`
   answers with the same shape for both of its intents.

**Technical approach**: additive. No new table, no new audit action, no new error code, no new
dependency, no change to any existing operation's contract.

## Technical Context

**Language/Version**: TypeScript 5 (strict), Node 24 LTS, pnpm

**Primary Dependencies**: Next.js App Router (standalone), Zod 4, `zod-openapi` (document
generation), Drizzle ORM (`drizzle-orm/node-postgres`), Vitest. No new runtime dependency.

**Storage**: Postgres. One migration: `ALTER TYPE "public"."api_key_permission" ADD VALUE
'manage_setup'` (generated by `pnpm db:generate`, precedent `drizzle/0032_dated_series_audit_actions.sql`).
No new table, no new column.

**Testing**: Vitest against a real Postgres (locally port 5555, see `docs/getting-started.md`), driving
the route module directly through `tests/helpers/api.ts` — no listening server. Integration tests per
operation, plus the existing cross-project scope test, the OpenAPI document test, the import-boundary
test and the secret scan, all extended rather than replaced.

**Target Platform**: Linux server (Docker Compose: web, worker, postgres) and Neon.

**Project Type**: Web service — one Next.js app with a server layer. The public API is one catch-all
route backed by an operation table.

**Performance Goals**: One service call per request; `SC-002`'s five HTTP calls to provision a brand.
The whole-week add is one request and at most two statements (list, then one multi-row insert). No
operation adds an N+1 read.

**Constraints**: Each operation calls exactly one service function (constitution IV) and reaches no
repository or database directly (constitution III, enforced by `tests/lint/api-imports.test.ts`).
Idempotency semantics are the existing ones (research D8: claim, run, store; 7-day retention). Error
answers must come from the existing `API_ERROR_CODES` list and must be byte-identical for a foreign
and a non-existent resource.

**Scale/Scope**: 7 new operations (today 26), 1 new key permission, ~8 new API schemas, 1 migration,
1 UI checkbox, 4 documentation files.

## Design decisions that shape the work

Full reasoning and the code citations behind each are in [research.md](./research.md); the list below
is what an implementer needs to hold in mind.

- **Eight paths, seven operations** (see [contracts/http-api.md](./contracts/http-api.md)):
  `POST /projects`, `POST /voice-profiles`, `PATCH /voice-profiles/{profileId}`,
  `PATCH /accounts/{accountId}`, `POST /slots`, `POST /slots/week`, `PATCH /slots/{slotId}`,
  `DELETE /slots/{slotId}` — all requiring `manage_setup`, all accepting `Idempotency-Key`.
- **Path parameters are named `{profileId}`, `{slotId}`, `{accountId}`**, not `{id}`: `parseInput`
  only pre-checks parameters whose name ends in `Id`, and that pre-check is what turns a non-UUID
  path segment into a 404 instead of a 400 (spec edge case). The URL shape is unchanged.
- **`POST /projects` runs with `idempotencyMode: "self_commit"`**, because `createProject` commits in
  its own cross-project transaction and cannot join the key project's idempotency transaction. The
  global unique constraint on `projects.slug` is the backstop: a replay that lost its stored result
  answers 409 `slug_taken` rather than making a second project.
- **The "no acting user" refusal is a null `api_keys.created_by_user_id`**, not a creator who merely
  left the project. Leaving the project does not clear the column, so such a key still creates
  projects (and its creator becomes the new project's owner); only a deleted user account leaves
  `scope.membership.userId` empty, and that is what FR-015 refuses. This corrects the spec's
  description of the trigger while keeping its requirement exactly.
- **Response schemas never contain a Zod transform.** `taglineSchema`, `brandDescriptionSchema`,
  `brandWebsiteSchema` and `voiceContentInputSchema` are transforms and belong in request bodies
  only; the project response declares plain nullable strings. A transform in an output position
  makes `createDocument` throw and would take the whole OpenAPI document down.
- **Every new operation declares its error statuses explicitly** (400, 401, 403, 404 where it can
  happen, 409, 422, 429) with an example each, through one shared helper, so FR-042 is satisfied
  uniformly. Pre-existing operations are not retrofitted (`docs/decisions.md` 009 note P11).
- **`PATCH /slots/{slotId}` takes a strict union**: `{weekday, localTime}` or `{paused}`. Both or
  neither is a validation failure, and each branch dispatches to exactly one service function.
- **`PATCH /accounts/{accountId}` takes a strict object** with one field, `instructions` (a string;
  `""` clears it). Any other key is a validation failure, which is FR-028 for free.
- **`POST /slots` and `POST /slots/week` take the account id in the body**, so the cross-project
  scope test (which only walks path parameters) does not cover them; they get their own
  foreign-versus-unknown equivalence test.
- **Documentation placement**: the provisioning example goes in `docs/n8n.md` **after** section 7.
  `tests/integration/docs/n8n-flow.test.ts` slices the file at `## 7. Recover failed posts` and
  asserts the exact list of request blocks before it; putting the new section earlier would break a
  passing test for no reason.

## Risks and how the design answers them

| Risk | Answer |
|---|---|
| Widening `ApiOperation.method` breaks the router or the document | Nothing in `matchOperation`, `allowedMethods` or the OpenAPI builder switches on the method, and `handle.ts` already lists `PATCH`/`DELETE` in `WRITE_METHODS`. The OpenAPI test already asserts "documents exactly the operations that are served", so a mismatch fails loudly. |
| The new permission silently widens an existing key | `KEY_GRANTS.manage_setup` grants only `project`, `account`, `slot` and `voice` rights, and the pipeline checks the operation's own permission first, so a key holding only `manage_setup` is refused by every pre-existing operation. FR-052's test asserts both directions. |
| `POST /projects` leaks the holder of a taken slug | The conflict is raised from the unique violation in the DAL with a fixed message and the new `slug_taken` reason; no path reads the holding project, so there is nothing to leak. FR-049's test compares the visible-holder and invisible-holder answers byte for byte. |
| A replayed provisioning run makes a second project | Idempotency replay in the normal case; the global slug constraint in the degenerate case. Both are asserted. |
| The enum migration cannot be applied | `ALTER TYPE … ADD VALUE` is already used by five migrations here (0004, 0006, 0008, 0019, 0032); `pnpm db:check` proves the snapshot matches the schema. |
| A transform schema in a response breaks the whole document | Response schemas are plain, and the OpenAPI test runs the real `@seriousme/openapi-schema-validator`, so a mistake fails the suite rather than production. |
| `GET /accounts` (the only way to read instructions back) changes shape | It is not touched. `AccountSchema` already carries `postingInstructions`, and the OpenAPI test already asserts that. |
