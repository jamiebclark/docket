# Data model: Instagram video

Phase 1 for `specs/019-instagram-video/spec.md`. Decisions are cited as P* from [research.md](./research.md) and D*/G* from the spec.

## 1. Schema (migration `0012`)

One migration, generated by drizzle-kit from `src/server/db/schema/*.ts` and committed. `pnpm db:check` must pass.

### 1.1 `post_targets.chosen_post_type` (G19, P3)

| Column | Type | Null | Notes |
|---|---|---|---|
| `chosen_post_type` | `text` | yes | The post type a person or API caller chose for this target. `NULL` = use the provider's default. |

- CHECK `post_targets_chosen_post_type_known`: `chosen_post_type IS NULL OR chosen_post_type IN ('text','image','carousel','video','story','reel')`. These are the `PostType` values. The CHECK stops unknown strings; which values a provider *offers* is checked in the service (P4).
- Existing rows get `NULL`, so every existing target keeps its inferred type. A single-video Instagram target with `NULL` resolves to Feed video (D2).
- `TargetRecord` gains `chosenPostType: PostType | null`. `TargetPatch` accepts it.

### 1.2 `allowance_uses` (G22, P23)

A project-owned ledger of creation-allowance reservations. It is append-only apart from housekeeping deletes.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | `uuid` PK | no | `gen_random_uuid()` |
| `project_id` | `uuid` → `projects.id` ON DELETE CASCADE | no | Constitution III |
| `social_account_id` | `uuid` → `social_accounts.id` ON DELETE CASCADE | no | The account whose allowance is used |
| `post_target_id` | `uuid` → `post_targets.id` ON DELETE SET NULL | yes | The target that reserved it, kept for the attempt log and tests. A deleted post does not give its containers back. |
| `units` | `smallint` | no | CHECK `units > 0` |
| `created_at` | `timestamptz` | no | The claim's DB clock (`opts.now`), not `now()`, so tests that pin the clock see the window move |

- Index `allowance_uses_account_created_idx` on `(social_account_id, created_at)`.
- **Written** only inside `claimDueTargets`'s transaction, through `ClaimContext.reserveAllowance`. **Read** there through `ClaimContext.allowanceUsed`. Both run inside the existing `crossProject("scheduler: claim due targets")` and filter on `project_id` as well as the account.
- **Deleted** by housekeeping when `created_at < now − 7 days`, through a `crossProject("housekeeping: prune allowance uses")` repo.
- The scope-check test (`tests/helpers/scope-check.ts`) must list the table as project-owned. Every query it sees carries `project_id`.

## 4. Instagram step state (`src/providers/instagram/state.ts`, P19)

```ts
instagramStateSchema = z.object({
  v: z.literal(1),
  mediaType: z.enum(["IMAGE", "CAROUSEL", "REELS"]),
  /** REELS only: true = Feed video, false = Reel. */
  shareToFeed: z.boolean().optional(),
  /** CAROUSEL only: kind of every planned item, in post order. Absent = all images (state saved before 019). */
  kinds: z.array(z.enum(["image", "video"])).min(2).max(10).optional(),
  items: z.array(z.string().min(1).max(100)).max(10),
  /** Aligned with `items` when `kinds` has a video; image entries are { ready: true, checks: 0 }. */
  itemProgress: z.array(z.object({ createdAt: z.string(), checks: z.number().int().min(0), ready: z.boolean() })).max(10).optional(),
  container: z.string().min(1).max(100).nullable(),
  createdAt: z.string().nullable(),
  checks: z.number().int().min(0),
  ready: z.boolean(),
  quotaChecked: z.boolean(),
  recreations: z.number().int().min(0).max(MAX_RECREATIONS),
});
```

**Plan** (derived, never stored on its own):

| Content (`kinds`, `postType`) | Plan |
|---|---|
| `["image"]` | `{ mediaType: "IMAGE" }` |
| `["video"]`, `postType` ≠ `reel` | `{ mediaType: "REELS", shareToFeed: true }` (Feed video, D1/D2) |
| `["video"]`, `postType` = `reel` | `{ mediaType: "REELS", shareToFeed: false }` |
| 2–10 items | `{ mediaType: "CAROUSEL", kinds }` |
| 0 or > 10 items | invalid (`INVALID_STEP`) |

**Valid state** for a plan (anything else returns `null`, which restarts the target, D13):

- `mediaType` equals the plan's.
- REELS: `shareToFeed` equals the plan's.
- CAROUSEL: `kinds ?? all images` equals the plan's `kinds`, and `items.length ≤ kinds.length`. When `kinds` has a video, `itemProgress.length === items.length`.
- The existing rules: `ready ⇒ container`, `quotaChecked ⇒ ready`.
- `container !== null ⇒ items.length === kinds.length` (CAROUSEL), and every video item is ready.

A state saved by the previous release (IMAGE, or CAROUSEL without `kinds`) is valid for an all-image plan, so in-flight image targets resume unchanged (FR-005, FR-018).

**Step derivation** (`instagramStepFor`):

```
plan invalid                         → invalid
s = validState(state, plan) ?? initialState(plan)
s.container === null:
  IMAGE | REELS                      → create_container              allowance {units: 1, retryUnits: 1}
  CAROUSEL, items < n                → create_item_<items+1>         allowance {units: items==0 ? n+1 : 0, retryUnits: 1}
  CAROUSEL, a video item not ready   → check_item_<k> (first such k)
  CAROUSEL                           → create_carousel               allowance {units: 0, retryUnits: 1}
!s.ready                             → check_status
!s.quotaChecked                      → check_quota
otherwise                            → publish (mayPublish: true)
```

`create_container` carries `units: 1` because it is always a build's first create. After `recreated()`, the state is a fresh build again, so the next lease of the first create step reserves the whole need again (P22).

**Transitions** (each `continue` sets `notBefore` to the next step's due time, P18):

| Step | Result | State change | `notBefore` |
|---|---|---|---|
| `create_container` (IMAGE) | id | `container`, `createdAt`, `checks: 0` | +10 s (unchanged) |
| `create_container` (REELS) | id | as above | +60 s |
| `create_item_<n>` (image) | id | `items += id`; `itemProgress += { createdAt: now, checks: 0, ready: true }` when `kinds` has a video | now, or the first unready video item's due time after the last item |
| `create_item_<n>` (video) | id | `items += id`; `itemProgress += { createdAt: now, checks: 0, ready: false }` | as above |
| `check_item_<k>` | `FINISHED` | `itemProgress[k-1].ready = true`, `checks + 1` | the next unready item's due time, or now |
| `check_item_<k>` | `IN_PROGRESS`, age < 60 min | `checks + 1` | now + `videoCheckDelayMs(age)` |
| `create_carousel` | id | `container`, `createdAt` | +10 s if all images, +60 s if any video |
| `check_status` | `FINISHED` | `ready`, `checks + 1` | now |
| `check_status` | `IN_PROGRESS` | `checks + 1` | images: `checkIntervalMs(checks)`; video: `videoCheckDelayMs(age)` |
| any check | `EXPIRED` | `recreated(s)` | now |
| `check_quota` | oldest container ≥ 23 h | `recreated(s)` | now |
| `check_quota` | under quota | `quotaChecked` | now |

The age for a video item is measured from that item's `createdAt`, and for a container from `createdAt`. "Oldest container" is the first video item's `createdAt` for a carousel with a video; otherwise it is `createdAt` (unchanged).

**Terminal results:**

| Where | Result |
|---|---|
| any check `ERROR` | `fatal_error` with the P20 message |
| video check, `IN_PROGRESS`, age ≥ 60 min | `fatal_error`: "Instagram did not finish processing the video within 60 minutes; nothing was published. Retry the post to try again." |
| image check, `IN_PROGRESS`, age ≥ 60 min | `fatal_error`: "Instagram did not finish processing the media." (unchanged) |
| any check `PUBLISHED` | `ambiguous` (unchanged) |
| any check, unknown code | `retryable_error` (unchanged) |
| `EXPIRED` or aged, `recreations = 2` | `fatal_error` (unchanged text) |
| `publish` | `done` / `ambiguous` / `fatal_error`, unchanged |

## 5. Requirements summary additions (`RequirementsSummary`, P13)

```ts
video: {
  // …existing fields, now computed from videoLimitsFor(caps, shownType)…
  minFrameRate: Labelled<number> | null;
  /** The type these limits are for; null when the provider declares no choice and no per-type limits. */
  postType: { value: PostType; label: string; description: string | null } | null;
  notes: string[];
};
/** Null when the provider has no carousel post type or does not accept video. */
carousel: {
  maxItems: number;
  /** Images and videos may share one carousel. */
  mixed: boolean;
  videoAspectRatio: Range;
  notes: string[];                       // Instagram: ["Reels cannot be carousel items."]
} | null;
```

For an Instagram single-video target set to Reel:
- `video.postType` is `{ value: "reel", label: "Reel", description: "Shown in the Reels tab only." }`;
- the labels read 3 seconds to 15 minutes, 300 MB, MP4 and MOV, H.264 and HEVC, AAC (silent allowed), 23–60 fps, up to 1920 px wide, aspect 1:100 to 10:1. `ratioLabel` gains a `1:n` form for ratios below 1:20 whose inverse is a whole number up to 1000, so 0.01 reads "1:100" and not "0.01:1" (US2-3).
- `carousel` is `{ maxItems: 10, mixed: true, videoAspectRatio: 4:5 – 1.91:1, notes: [...] }`.

## 6. Composition and API views

- `TargetCheck` (`src/server/services/posts/compose.ts`) gains `postTypeChoice: { options: PostTypeOption[]; selected: PostType; default: PostType } | null`. It is present only when `choiceFor(caps, media)` is not null. `selected` is the resolved type. `TargetCheck.postType` becomes the resolved type, and `requirements` is built for it.
- `postTargetInputSchema` gains `postType: z.enum(POST_TYPES).nullish()`. An absent field keeps the stored value and `null` clears it (P3).
- The API's `createPost` body gains `postTypes: z.record(z.uuid(), z.enum(POST_TYPES)).optional()`. `TargetSchema` gains `postType: z.string().nullable()` (effective, P7).
- `TargetContent` (`src/server/services/posts/validate.ts`) gains `chosenPostType: PostType | null`.
- `ClaimContext.contentShape` returns `kinds` (by `post_media.position`) and `chosenPostType` besides today's fields. `ClaimContext` gains `allowanceUsed(accountId, projectId, since)` (returns `{ at, units }[]` oldest first) and `reserveAllowance({ accountId, projectId, targetId, units })`.
