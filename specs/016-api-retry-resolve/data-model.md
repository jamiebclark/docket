# Data model: Public API to retry, bulk-retry and resolve targets

**Feature**: `016-api-retry-resolve` | [plan.md](./plan.md) | [research.md](./research.md)

One schema change: two nullable columns. The other entities are request and response shapes, specified in [contracts/http-api.md](./contracts/http-api.md). This file covers what is stored and the rules that apply to it.

## 1. Schema change (migration `0010_api_key_attribution`)

| Table | New column | Type | Null | Constraint | Written by |
|---|---|---|---|---|---|
| `publish_attempts` | `actor_api_key_id` | `uuid` | yes | FK `publish_attempts_api_key_fk`: `(project_id, actor_api_key_id) → api_keys(project_id, id)`, `ON DELETE no action` | `attempts.insert` via `attemptActor(scope)` |
| `post_targets` | `resolved_by_api_key_id` | `uuid` | yes | FK `post_targets_resolver_api_key_fk`: `(project_id, resolved_by_api_key_id) → api_keys(project_id, id)`, `ON DELETE no action` | `resolveAmbiguous` via `resolverColumns(scope)` |

- **Drizzle schema**:
  - `src/server/db/schema/attempts.ts` gains `actorApiKeyId: uuid("actor_api_key_id")` and the FK in the table's extra-config array, importing `apiKeys`;
  - `src/server/db/schema/posts.ts` (`postTargets`) gains `resolvedByApiKeyId: uuid("resolved_by_api_key_id")` and the FK;
  - check for an import cycle: `api.ts` must not import `attempts.ts`.
- **SQL**: generated by `pnpm db:generate --name api_key_attribution`, then committed with its `meta/0010_snapshot.json` and `_journal.json` entry. `pnpm db:check` must stay green.
- **Existing rows**: null. No backfill (spec Assumptions).
- **No index**: reads go from target to attempts, through the existing `publish_attempts_target_created_idx`, and never from key to attempts.
- **Project isolation**: both tables already carry `project_id`, and the composite FK pins the key to the same project. The scope-check test (`tests/integration/scope-check.test.ts`) needs no change, because the repositories' filters are unchanged.

## 2. Attribution values (FR-020–FR-024, research P5)

`actorRefs(scope)` is the one helper in `src/server/dal/scope.ts`:

| Scope | `userId` | `apiKeyId` |
|---|---|---|
| Member (UI) | `membership.userId` | `null` |
| API key, creator's user row exists (member or not) | `key.createdByUserId` | `actor.apiKeyId` |
| API key, creator's user deleted (`created_by_user_id` set null) | `null` (never `""`) | `actor.apiKeyId` |
| Job runner | `actorUserId` or `null` | `null` |

The other helpers are derived from it:

- `actorColumns(scope)` returns `{ createdByUserId, createdByApiKeyId }`. Same values as today.
- `attemptActor(scope)` returns `{ actorUserId, actorApiKeyId }`. It is spread into every `attempts.insert` in `posts/retry.ts` and `resolveAmbiguous`.
- `resolverColumns(scope)` returns `{ resolvedByUserId, resolvedByApiKeyId }`. It is spread into `resolveAmbiguous`'s `common` patch.

`AttemptEntry` (`src/server/dal/attempts.ts`) gains `actorApiKeyId?: string | null`, which `insert` writes as `?? null`. `TargetPatch` picks up `resolvedByApiKeyId` from the schema type.

**Invariant**: an attempt entry or resolution written through an API key always has a non-null key column. One written by a member or the engine always has a null key column.

## 3. Attempt entry view (FR-023, research P7)

`AttemptEntryView.actor` (`src/server/services/failures.ts`):

```text
{ kind: "api_key"; name: string | null }   // actorApiKeyId set; name from apiKeys.get, null if not found
| { kind: "member"; name: string }         // no key, actorUserId set; member name or "Former member"
| { kind: "system" }                       // neither
```

The key always wins over the user column. `attemptActorLabel(actor)` (`src/lib/failures/attempt-actor.ts`, pure) renders:

| Actor | Label |
|---|---|
| `api_key`, name present (active, revoked or expired key) | `API key {name}` |
| `api_key`, name null | `Removed API key` |
| `member` | `{name}` (unchanged, including `Former member`) |
| `system` | `System` (unchanged) |

The view never reads `last4`, `keyHash` or permissions (FR-026).

## 4. State transitions exposed (unchanged; for reference)

These are exactly 012, 015 and the resolve flow on `main`. The API adds no transition.

| Operation | From | Outcome | To | Attempt entries (`step: "user"`) |
|---|---|---|---|---|
| retry `now` | `failed` | scheduled | `scheduled` (next attempt now) | `retry_requested` (empty summary) |
| retry `requeue` | `failed` | scheduled | `scheduled` (slot occurrence held) | `retry_requested` `{ mode, scheduledAt, slotId, expected? }` |
| retry `requeue` | `failed` | `no_active_slots` / `no_free_occurrence` | `failed`, `last_error` = "Not retried — …" | `retry_requested` `{ mode, reason }`, `error: no_free_slot` |
| retry `requeue`/`at` | `failed` | `validation` / `account_unavailable` | unchanged | none |
| retry `at` | `failed` | scheduled | `scheduled` (explicit) | `retry_requested` `{ mode, scheduledAt }` |
| retry `at` (not future) | `failed` | `in_past` | unchanged | none |
| retry, any mode | `publishing` / not `failed` / blocked account | 409 | unchanged | none |
| resolve `published` | `ambiguous` | published | `published`, `resolved_*` set | `resolved_published` |
| resolve `not_published`, no requeue | `ambiguous` | `not_requeued` | `failed`, `resolved_*` set | `resolved_failed` |
| resolve `not_published`, requeue, slot | `ambiguous` | scheduled | `scheduled`, `resolved_*` set | `resolved_not_published`, then `requeued` (+1 ms) |
| resolve `not_published`, requeue, no slot | `ambiguous` | `no_free_slot` | `failed`, `resolved_*` set | `resolved_not_published`, `error: no_free_slot` |
| resolve, gate refused | `ambiguous` | 409 `cannot_publish` | unchanged | none |
| resolve | not `ambiguous` | 409 `already_resolved` | unchanged | none |
| bulk | each `failed` target | per 015 | per single retry | per single retry |

Each change runs `applyDerivedStatus`, which emits `post.published` / `post.failed` in the same transaction when the post's derived status changes (FR-025).

## 5. Refusal reasons (FR-011, research P4)

`ConflictError.reason` is set at these existing throw sites. The sentences are unchanged.

| Reason | Thrown by | Sentence |
|---|---|---|
| `publishing` | `retryLockedTarget` | Publishing in progress. Try again in a moment. |
| `not_failed` | `retryLockedTarget` (status check and `lost()`) | This post is no longer failed. |
| `account_removed` | `retryLockedTarget` via `retryBlockedKey` | This account was removed, so the post can't be retried. |
| `needs_reconnecting` | same | {Account} needs to be reconnected before this post can be retried. |
| `provider_unavailable` | same | The provider for {Account} is no longer available. |
| `already_resolved` | `resolveAmbiguous` (status check and `lost()`) | This post was already resolved. |
| `cannot_publish` | `resolveAmbiguous` (requeue gate) | the gate's message, for example "{Account} needs to be reconnected." |

## 6. Validation rules (request side)

The full shapes are in [contracts/http-api.md](./contracts/http-api.md).

- All three bodies are strict objects. An unknown key is `400 validation_failed`.
- `mode` / `outcome` / `requeue` are required discriminators. There are no defaults (D5).
- `at` and `expected` are RFC 3339 with an offset (`atSchema`). Resolve `expected` is normalised to UTC before the service call (P9).
- `url` uses `externalUrlSchema`: an external http(s) URL of at most 2048 characters. Errors are reported at `path: "url"`.
- `accountId` is a UUID. An unknown or foreign one is accepted and matches nothing (FR-016).
- Path ids are UUIDs. A non-UUID is `404` (pipeline F2). A pairing mismatch is `404` (P3).
