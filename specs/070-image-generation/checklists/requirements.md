## Notes

- **On "no implementation details"**: this repo's specs deliberately carry code grounding, because the
  constitution's first principle is "verified facts over memory" and a phase that cannot reach the web
  needs the file it is talking about named. The grounding is confined to **Context and sources** and
  **Decisions made while specifying**; the 38 functional requirements and 10 success criteria state
  behaviour ("MUST be refused with exactly the sentence…", "an editor cannot cause an image to be
  generated by any route"), not mechanism. Matches `specs/069-brand-profile-fields/spec.md` and
  `specs/065-per-project-llm/spec.md`.
- **Four deliberate exceptions**, each because the roadmap entry or the constitution makes it an
  acceptance condition rather than a mechanism: FR-003 (no model identifier in source — the roadmap
  names the guard test), FR-004 (the key stays readable in one file — constitution VII, existing guard),
  FR-010 (the vendor-specific parts live in one swappable adapter — the roadmap's "make the provider
  swappable"), and FR-025 (`pnpm db:check` green on the committed migration — a constitutional quality
  gate, the same exception 069's FR-001 took).
- **Two corrections to the input**, both recorded as decisions and in "Facts":
  - The roadmap says "the project's own voice profiles already forbid using a real child's likeness".
    No such rule exists anywhere in `src/` or `docs/` — it lives in one install's voice-profile *content*,
    which is operator data. G14 therefore adds the rule in code for the first time rather than relying
    on data a different install would not have.
  - The roadmap asks for an "owner/admin-visible" action, but both plausible existing permissions
    (`media: ["edit"]`, `generation: ["run"]`) are held by editors too. G22 adds one new owner/admin
    statement rather than widening who can spend the project's image budget.
- **Two `NEEDS RESEARCH` markers, not `NEEDS CLARIFICATION`**: the exact error identity of a
  content-policy refusal on the images endpoint, and the latency and price of an image call. Neither is a
  question for the user — both are external facts a phase that cannot reach the web must not guess
  (constitution I), and the design is written so that neither blocks: an unrecognised refusal classifies
  as a generic rejected request (FR-011) and nothing depends on a latency number (Assumptions).
- **No clarification questions were needed.** Every gap had a defensible default, recorded as G1–G26.
  The three that most changed the shape of the feature: image configuration is separate from text
  configuration (G1 — Anthropic ships no image API, so reusing `LLM_PROVIDER` would deny images to
  Anthropic installs); an image call spends the project's own credential only when that project's chosen
  vendor *is* the image vendor (G9 — an install may have no provider of its own at all, so an
  install-only rule would deny images to exactly those installs); and image calls are recorded in the
  existing usage ledger (G12 — the one call expensive enough that leaving it out would make the Usage
  screen wrong where it matters most, at the price of one enum value and one widened guard test).
- Validated in one pass. Three wordings were tightened during it: SC-002 and SC-007 were restated as
  observable outcomes rather than code-shape claims, and the "abandoned request" edge case was corrected
  — leaving the page does not cancel work already in flight, so the honest requirement is that no
  *half-made* asset can exist, not that no asset appears.
