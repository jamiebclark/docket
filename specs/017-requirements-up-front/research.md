# Research: Requirements up front (017)

Phase 0 for [plan.md](./plan.md). Platform facts come only from `docs/research/` (constitution I). Code facts were read from `main` at `b3277ff` in this phase. Library facts were probed in Node 24 in this phase. The spec has no `NEEDS CLARIFICATION` items. This file settles the open implementation questions as plan decisions **P1–P15**, which are recorded in `docs/decisions.md` under `## 017`.

## Facts confirmed in the code (F)

- **F1 — The composer already checks an empty composer.** `Composer.tsx` runs `fetchCheck` whenever `targets` (the selected accounts) change, with `baseText` `""` and no media, and skips the request only when no account is selected. `postInputSchema` defaults `baseText` to `""`. So the spec's first assumption holds: a summary attached to the check response shows as soon as an account is selected (FR-002, SC-002). No change to *when* the check runs.
- **F2 — One validation path.** `validateTargetContent` (planner → `adaptedMediaFor` → `validateResolvedContent` → merge) serves the composer check (`preview: true`), the scheduling gate and, through `validateResolvedContent` and `resolvePublishMedia`, the engine's publish-time re-validation. Anything added to `validateAgainstCapabilities` therefore reaches all three check points (FR-011, SC-006).
- **F3 — Every provider's `validate` calls `validateAgainstCapabilities`.** Instagram, Facebook, Threads, X, Bluesky and mock all start from it. Instagram rewrites `text_only_not_allowed` and excuses PNG and oversize files, but passes every other issue through unchanged.
- **F4 — The planner is pure and already shared.** `planImage(asset, mediaConstraintsOf(caps), ctx)` decides `original | derive | refuse`. `media-variants.ts` wraps it in a private `planFor`, which plans an asset **without dimensions** as `original` ("goes as is and the provider's own checks apply"). Production uploads always have dimensions: `processUpload` refuses a file that does not decode ("That file could not be read as an image.") or has zero width or height. Only rows inserted without dimensions lack them, and today only tests do that (`createMediaAsset` and the test-only `registerAsset`).
- **F5 — Publish limits are read only through `providerPublishLimits`.** The engine's deferral and the generated limit rows use it. Changing `INSTAGRAM_DEFAULT_PUBLISH_LIMIT` is the whole enforcement change. `tests/integration/instagram/limits.test.ts` hard-codes 100 publishes and must move to 50.
- **F6 — The run-time Instagram quota read exists.** It lives in `src/providers/instagram/quota.ts` and the `quota` step (`quota_usage`, `config.quota_total`, hold ≥ 1 h when spent). FR-013 leaves it unchanged.
- **F7 — Meta rate-limited codes.** `src/providers/meta/errors.ts` has `rateLimited: [4, 17, 32, 613, 80001, 80002]`, shared by Facebook, Instagram and Threads, with a test per code. No code change (FR-021).
- **F8 — The doc-inventory test** (`tests/integration/docs/limits-inventory.test.ts`) derives a category → value map from capabilities (`declared()`) and requires `docs/limits.md` to list exactly those rows. Each row must cite a test generated by `tests/helpers/limit-rows.ts` in the suite for its enforcement point. A new capability field therefore needs: a category in `declared()`, a generated row in `limit-rows.ts`, and a row in the doc and in its "How to read a row" vocabulary (FR-019).
- **F9 — The provider guide test** (`tests/integration/docs/provider-guide.test.ts`) requires every member of `ProviderCapabilities` to appear in a code span in `docs/adding-a-provider.md`. New capability fields must be documented there.
- **F10 — Literals in UI today.** `MediaCard.tsx` has a MIME→label map (`TYPE_LABEL`). `MediaPicker.tsx` and `UploadDropzone.tsx` have `accept="image/jpeg,image/png,image/webp"`. `UPLOAD_MIME_TYPES` lives in `src/server/services/media.ts`, which a client component cannot import at run time. The composer itself has no limit literals: it reads `count`, `limit` and `countingRule` from the check.
- **F11 — The library list is one service call.** Both the media page (server component) and the picker (`listMediaAction` → `listMedia`) call `listMedia(scope, filter)`, which returns one page of `MediaView`s (24 items). The stored `mimeType`, `width`, `height` and `byteSize` on each row are all the planner needs, so no image is re-read (spec assumption).
- **F12 — Probed in this phase.** In Node 24, the regexes in P4 give these counts: `"#a #b #a"` → 3; `https://example.com/#top`, `#`, `#123` and `C#` → 0; `(#tag)` → 1; `##tag` → 1; `café #été` → 1; `a@b.com` and `first.last@example.co.uk` → 0 mentions; `https://x.com/@user` → 0; `hi @bob and (@ann)` → 2; `@bob.` → 1; `#tag#two` → 1. They use `u`-flag lookbehind and `\p{…}` classes.

## Decisions (P)

### P1 — The summary is a pure function of capabilities, attached to each target of the check

- **Decision:** a new pure module `src/providers/requirements.ts` exports `requirementsOf(caps, { uploadTypes })` → `RequirementsSummary`, with `text`, `image` and `post` parts (D10). `checkComposition` adds `requirements: RequirementsSummary | null` to every `TargetCheck`. The value is `null` only when the provider is not registered, the same condition that makes `limit` `null` today. `uploadTypes` is `UPLOAD_MIME_TYPES`, so the summary can say which uploads are converted.
- **Rationale:** D1 puts the summary on the check. A pure function in `src/providers/` can be unit-tested against every registered provider (SC-001). It obeys the import boundary (providers import nothing from `src/server`), and the text part reuses `countingRuleName`/`countingUnit` from `text.ts`, the functions the counter and the `text_too_long` message use (FR-004).
- **Alternatives:** building the summary inline in `compose.ts` (not reusable by entry 2's video part, and harder to test per provider); a separate endpoint or the account view (rejected by D1).

### P2 — Display labels are computed on the server; the UI only words sentences

- **Decision:** the summary carries a display `label` next to each machine value:
  - MIME types become `JPEG`, `PNG` or `WebP`;
  - aspect ratios become `4:5` or `1.91:1`, through `aspectLabel(r)`: if `r < 1` and a fraction `a:b` with `b ≤ 20` equals `r` within 1e-9, it is `a:b`, otherwise `r:1`. So 0.8 → `4:5`, 0.1 → `1:10`, 10 → `10:1`;
  - byte limits become decimal megabytes (`8 MB`, `2 MB`, `10 MB`), matching the providers' decimal convention (D4).

  The MIME label map and `UPLOAD_MIME_TYPES` move to a new client-safe `src/lib/media/types.ts`, with the same values. `src/server/services/media.ts` re-exports `UPLOAD_MIME_TYPES`, so existing imports keep working. `src/providers/media.ts`, `MediaCard.tsx`, `MediaPicker.tsx` and `UploadDropzone.tsx` import from it, the last two for their `accept` attribute.
- **Rationale:** SC-004 asks for zero format or limit literals in composer, picker and media-library UI code, and F10 found three. Moving the constants changes no value: the uploadable types stay JPEG, PNG and WebP, so FR-023 (no new upload MIME types, no transport change) holds.
- **Alternatives:** leaving `accept` literals as "upload, not platform" (fails SC-004 as written); labels in the client (a second MIME map in UI code).

### P3 — Caption rules are optional text capabilities, enforced by the shared validator

- **Decision:** `ProviderCapabilities.text` gains `maxHashtags?: number` and `maxMentions?: number`. Instagram declares 30 and 20 (`INSTAGRAM_MAX_HASHTAGS`, `INSTAGRAM_MAX_MENTIONS`). `validateAgainstCapabilities` counts with `countHashtags`/`countMentions` (new, in `src/providers/text.ts`). Past a limit it adds an `error` with code `too_many_hashtags` or `too_many_mentions`, `field: "text"`, `count` and `limit`, and the message "The caption has 31 hashtags; the limit is 30." (or "… @mentions …"). The new issues sit right after `text_too_long` in the stable order.
- **Rationale:** F2 and F3 mean one change reaches the composer check, the scheduling gate and the engine re-validation (FR-011, SC-006) with no per-caller code (constitution IV). An optional field means no other provider changes (constitution V).
- **Alternatives:** an Instagram-only check in `validateInstagram` (works, but the "caption rules" entity is generic and the summary should read it from capabilities); a nested `text.caption` object (one more level for two numbers).

### P4 — What counts as a hashtag or a mention (FR-012)

- **Decision:**
  1. Mask URLs (`scheme://…` and `www.…` up to the next whitespace) and email addresses (`local@domain.tld`) with a space before counting.
  2. A hashtag is `#` at the start, or after whitespace, punctuation or a symbol (`\p{P}`, `\p{S}`), followed by one or more `[\p{L}\p{N}_]` with at least one non-digit.
  3. A mention is `@` in the same position, followed by one or more `[\p{L}\p{N}._]` with at least one letter, digit or underscore (so `@.` alone does not count).
  4. Every occurrence counts, repeats included (D7).

  The probed regexes are in F12. `#tag#two` counts once, because the second `#` follows a letter. That is the FR-012 rule, and it matches the `C#` case.
- **Rationale:** these are FR-012's rules, written down. Letters are Unicode, so `#été` counts: over-counting is the safe side under D7.
- **Alternatives:** ASCII-only letters (would miss `#été`, which Instagram counts); counting unique tags (rejected by D7).

### P5 — A fit badge is computed by one pure function that reuses the gate's per-image path

- **Decision:** a new `src/server/services/media-fit.ts` exports a pure `fitOf(asset, provider)` → `PlatformFit`. It:
  1. plans the asset with the same `planFor` the gate and the publish path use (exported from `media-variants.ts`, with an optional label, P6);
  2. builds the item the composer check would validate. That is the original for `original` and the planned output for `derive`, exactly as the `preview` branch of `adaptedMediaFor` does; the two share one extracted pure helper;
  3. runs `validateResolvedContent(provider, { text: "", media: [item] })` and keeps only `error` issues on `media.0` whose code is not about alt text (`alt_text_too_long`, `missing_alt_text`).

  The state is `refused` when the plan is `refuse` (reasons: the planner's issues) or when step 3 left an error (reasons: those messages). Otherwise it is `converted` when the plan is `derive` (steps and the planner's notes) and `fits` when it is not.
- **Rationale:** FR-010 asks for the planner's own decision, computed on the server, with nothing re-implemented. For every asset with dimensions, which is every uploaded asset (F4), steps 2 and 3 add nothing beyond the planner, so the badge equals the plan, and the SC-003 test asserts exactly that. For a row without dimensions, the planner sends the original and the provider's own type check then decides, so a dimensionless WebP for Instagram reads "will be refused" and a dimensionless JPEG reads "fits". That is what publishing would do. Alt text is left out because it belongs to the image's description, not the file, and the composer already reports it.
- **Spec discrepancy, recorded:** the spec's edge case says an image with unknown dimensions or one that cannot be decoded is "refused … as the planner refuses undecodable images". In the code, undecodable files never reach the library, because the upload refuses them (F4), and the planner sends a dimensionless row as is. The badge follows the code, since FR-010 requires it to equal what publishing does. SC-003's "undecodable" case is therefore tested twice. A file that does not decode is refused at upload with `processUpload`'s message, so it never gets a badge. A dimensionless row gets the badge the publish path implies.
- **Alternatives:** calling `validateTargetContent` per image (a DB variant lookup per image and platform, about 144 queries per library page, for the same answer); a planner-only badge (would say "fits" for a dimensionless WebP that scheduling then refuses).

### P6 — Planner messages can name "This image" instead of "Image 1"

- **Decision:** `planImage`'s `ctx` gains an optional `label` (default `Image ${index + 1}`), and `planFor` passes it through. `fitOf` passes `"This image"`. Every existing caller passes no label, so its messages and decisions are unchanged.
- **Rationale:** the spec lets a badge shorten the planner's reason but not invent one. "Image 1 is too wide for Instagram" is wrong in a library grid. The planner still writes the sentence.
- **Alternatives:** stripping the prefix with a regex in the UI (re-implements the planner's wording in the client).

### P7 — Which platforms get badges

- **Decision:** `fitPlatforms(scope, sel)` in `media-fit.ts` turns a selection into the providers to badge:
  - `{ accountIds }` (the picker) reads each id through `scope.accounts.get` and ignores ids that are unknown or not in this project, without saying so;
  - `{ active: true }` (the library) uses `scope.accounts.list()` filtered to `status === "active"`.

  Accounts whose provider is not registered are dropped. The rest are deduplicated by provider key (D8) and sorted by provider display name.
- **Rationale:** D8 and D9. The picker includes `needs_reauth` accounts because the composer still shows them as targets. Ignoring foreign ids matches the project-scoping rule (constitution III) without telling a caller which ids exist.
- **Alternatives:** a 404 for a foreign id (the picker would lose its whole list over one stale id).

### P8 — Fits travel with the existing library list; no new route

- **Decision:**
  - **Input.** `listMedia`'s schema gains an optional `fit`, either `{ accountIds: uuid[] (≤ 50) }` or `{ active: true }`.
  - **Output.** Its result gains `platforms: { key, name }[]`, and each item gains `fit: PlatformFit[]` in `platforms` order. Without `fit`, both are empty.
  - **Callers.** The media page passes `{ active: true }`. `listMediaAction` forwards `fit` from the picker, which sends the composer's selected account ids, and the picker re-queries when they change.
- **Rationale:** one call already returns exactly the page of images that needs badges (spec assumption). Nothing new to authorise: `listMedia` already requires `media: view`, and `fitOf` reads only capabilities.
- **Alternatives:** a separate `/media/fit` route (a second round trip per page, and a second authorisation surface).

### P9 — UI: a compact summary per account and text badges per image

- **Decision:**
  - **`RequirementsSummary`.** A new component in `src/components/compose/RequirementsSummary.tsx` renders inside each preview card, below the counter. It shows one visible line ("2,200 characters · up to 10 images · JPEG") and a `<details>` with the full `<dl>`. The details start open when one account is selected and closed otherwise. The summary sits outside the preview's `aria-live` region, so checks are not re-announced.
  - **`FitBadges`.** A new component in `src/components/media/FitBadges.tsx` renders one `Badge` per platform: "Instagram: fits" (success), "Instagram: will be converted" (info) or "Instagram: will be refused" (danger). Below the badges, a list gives each non-fitting platform's planner sentence. It is plain text, so it works with screen readers and the keyboard and needs no tooltip.
  - **Wording.** Pure wording helpers (`requirements-ui.ts`, `fit-ui.ts`), unit-tested like `retry-ui.ts`, build every sentence from the data.
- **Rationale:** FR-007 and the `docket-ui` skill: text plus colour, never colour alone; no tooltips (not keyboard reachable); compact when several accounts are selected; the counter and issues stay where they are.
- **Alternatives:** a summary in the Accounts card (separates it from the account's preview); tooltip badges (not accessible).

### P10 — Limits vocabulary and generated rows for the caption rules

- **Decision:**
  - **Vocabulary.** Add the categories `hashtags` and `mentions` to `declared()` in the inventory test (only when declared) and to the "How to read a row" list in `docs/limits.md` (FR-019).
  - **Generated rows.** `coreRows` generates `<key>: hashtags` (text with `max + 1` hashtags, refuse `too_many_hashtags`) and `<key>: mentions` likewise, with the required image when media is required. `textRows` also takes these two categories, so the end-to-end suite proves the refusal at scheduling and at publish time with no platform request (SC-006).
  - **Rows.** The Instagram rows are `hashtags | 30 | per occurrence (FR-012) | docs/research/meta.md ("Limits verification, 2026-10-07") | validateResolvedContent | … "instagram: hashtags"`, and `mentions` likewise.
  - **Boundary tests.** The "exactly 30 and 20 is never blocked" half of SC-006 goes in literal unit tests in `src/providers/validation.test.ts` and `tests/integration/compose/check.test.ts`.
- **Rationale:** F8. The generated rows use the provider's own values, so a later change to 30 or 20 cannot drift from the doc.

### P11 — Instagram minimum width is a planner refusal only

- **Decision:** declare `minWidth: 320` in `instagramCapabilities`. `plannerRows` then generates `instagram: min width` (refuse `image_too_small`) automatically. The doc gains the `min width | 320` row, the `max width` row drops "scaled outside" and "narrower is accepted", and the audit note "Instagram minimum width 320 is not declared" is replaced (FR-014, FR-018, FR-020). `validateInstagram` does not change: the planner runs before it on every path (F2).
- **Check:** with `maxWidth` 1440, a downscale never makes the width less than 320, so the planner's "cannot be resized … without becoming too small" branch cannot fire for Instagram. Existing tests that relied on narrow images reaching Instagram (implement greps `instagram` with widths under 320) must move to 320 or wider.

### P12 — Researched value changes are single constants

- **Decision:**
  - **Instagram.** `INSTAGRAM_DEFAULT_PUBLISH_LIMIT` becomes `{ count: 50, windowSeconds: 86_400 }` (D2, FR-013). Its comment cites the 50-versus-100 contradiction.
  - **Facebook bytes.** `FACEBOOK_MAX_BYTES_PER_FILE` becomes `10_000_000` (D4).
  - **Facebook text and photos.** The comments on `FACEBOOK_MAX_TEXT` and `FACEBOOK_MAX_IMAGES` become "UNVERIFIED (not documented by Meta, checked 2026-10-07)" (D5, FR-016).
  - **Other comments.** The Instagram text comment cites the research and notes that the counting method is not documented. The Facebook formats comment cites the research (D3).
  - **Tests.** `tests/integration/instagram/limits.test.ts` moves from 100 to 50. Its fake `quota_total` stays 100, so the test still shows Docket's own counter, not Meta's, holding the line.
- **Rationale:** constitution I: the values come from `docs/research/meta.md` "Limits verification, 2026-10-07" and `docs/research/x.md`. Every enforcement path reads these constants (F5).

### P13 — A literal scan proves SC-004

- **Decision:** a new `tests/lint/ui-limit-literals.test.ts` reads the composer files (`src/app/p/[projectSlug]/compose/*.tsx` and `composer-logic.ts`), the picker, the media library page and its components, and the new `src/components/compose/*` and `FitBadges` files. It fails on any of:
  - an `image/…` string literal;
  - a counting rule name (`graphemes`, `code_points`, `utf8_bytes`, or a registered custom rule's `name`) as a string literal;
  - a numeric literal equal to any registered provider's declared limit of 100 or more (text lengths, byte limits, widths, alt text, publish counts).

  Smaller numbers are not scanned, because `size-20`-style values would give false positives. The summary test (SC-001) already proves that those values come from the data.
- **Rationale:** SC-004 needs a test, not a review promise.
