# Security findings

The record of the 010 security pass (FR-028). One row per area checked. Every row is either **Fixed** (with the test that proves it) or **Accepted** (with the written reason). None is left open. `tests/integration/docs/security-findings.test.ts` checks that every row names tests that exist and that every area in FR-028 is covered.

Severity is what the finding would have been without the fix: **high** (data or account exposure), **medium** (needs another weakness to be exploitable), **low** (hardening or defence in depth), **none** (checked, nothing found).

| Area | What was checked | Finding | Severity | Fix or accepted reason | Test |
|---|---|---|---|---|---|
| Secrets in logs | Console, stdout and stderr during one scanned run: first-user setup through the setup service, a real sign-in through the auth handler, a Bluesky connect (right and wrong password), Meta and Threads sign-in started and called back on that session with token exchanges whose errors echo the app secret, four Bluesky publishes (success, rejection echoing a token, two unknown outcomes), resolving those two (published with a link; not published and requeued), API key, invitation and webhook creation, webhook delivery, route calls and page renders. Secrets: `BETTER_AUTH_SECRET`, `CREDENTIALS_ENCRYPTION_KEY` (also as hex), `TICK_SECRET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `META_APP_SECRET` and `THREADS_APP_SECRET`; a Bluesky app password and its access and refresh tokens; the first-user setup password; a real Better Auth session token; an API key, a webhook secret and an invitation token, each in raw, base64, base64url, URL-encoded and hex forms. Not scanned: the database URL's password, `BOOTSTRAP_ADMIN_PASSWORD` (the env bootstrap path; setup through the setup service is scanned instead) and `MINIO_ROOT_PASSWORD` (Compose only) | No secret reaches a log. The scan itself is proven able to fail by a deliberate leak | none | Accepted: nothing found; the scan stays as a regression guard | `tests/integration/security/secret-scan.test.ts`, `tests/integration/bluesky/no-secrets.test.ts`, `tests/integration/meta/no-secrets.test.ts` |
| Secrets in responses | Status, headers and body of `GET /api/v1/posts` (right and wrong key), the tick route (right and wrong secret), health, compose-check, sign-in (real user, unknown user, wrong password) and `get-session` for the signed-in user, plus the service results of setup, connect, the Meta and Threads start and callback, and resolution, all in the same scanned run and for the same secrets | No secret appears outside its own issuing response | none | Accepted: nothing found. The allowed appearances are asserted separately and taken out by location: the API key and webhook secret creation results, the invitation link, and the session token's sign-in `Set-Cookie` and the two JSON fields in the next row | `tests/integration/security/secret-scan.test.ts`, `tests/integration/no-plaintext.test.ts` |
| Secrets in rendered UI | Accounts, API keys, webhooks, members and failures pages, rendered for the signed-in setup user after the scanned run | No secret is rendered. | Secrets in attempt logs and audit rows | `publish_attempts`, `post_targets`, `connect_attempts`, `webhook_deliveries` and their attempts, social account rows (without the ciphertext column) and `membership_audit_log`, for the scanned run's project | No secret stored. Provider error text that echoes a token is redacted before it is stored | none | Accepted: nothing found | `tests/integration/security/secret-scan.test.ts`, `tests/integration/bluesky/no-secrets.test.ts`, `tests/integration/meta/no-secrets.test.ts` |
| Audit log write paths | The audit guard sat in a service helper, so code that wrote through the repository directly (invitations) skipped it | The secret-key guard could be bypassed by any caller that did not go through `recordAudit` | low | Fixed: the guard now runs inside the repository's `insert`, the only write path, and the service helper delegates to it (FR-027, D21) | `tests/integration/audit.test.ts` |
| Error messages | Results returned to the UI and API after a wrong Bluesky password, a rejected publish whose platform message echoes a token, Meta and Threads token exchanges whose platform error echoes the app secret, a repeated setup, and wrong sign-in passwords | No error message carries a credential | none | Accepted: nothing found | `tests/integration/security/secret-scan.test.ts` |
| CSRF | Cross-origin and missing-Origin requests to a server action, a session route handler and the auth endpoints | Nothing in the app checked `Origin` itself. Better Auth checks it only when the request carries cookies, so a cookie-less login request from another site was accepted | medium | Fixed: `src/proxy.ts` refuses, with a bare 403 and no side effect, any state-changing request whose `Origin` differs from the public URL, whose `Sec-Fetch-Site` is cross-site, or that has a session cookie and no `Origin`. Bearer-authenticated API and tick calls are exempt (D16) | `tests/integration/security/csrf.test.ts`, `src/lib/http/same-origin.test.ts` |
| Tick secret | Missing, wrong, query-string and unset secrets | An unset secret answered 404 and a wrong one 401, which told a probe whether the endpoint was enabled. A secret in the query string would have been logged by proxies | low | Fixed: every refusal is the same 401 with the same bytes; the secret is compared as SHA-256 digests with `timingSafeEqual`; a query string is refused; the presented value is never logged (D18) | `tests/integration/tick-endpoint.test.ts` |
| Webhook secrets | Storage, display and signing of endpoint secrets | Secrets are stored encrypted with the endpoint as associated data, shown once at creation or rotation, and rotation keeps the old one for a 24 hour overlap | none | Accepted: nothing found | `tests/integration/webhooks/settings.test.ts`, `tests/integration/webhooks/rotation.test.ts` |
| Webhook destinations | Save-time and delivery-time handling of loopback, link-local, unspecified and reserved addresses | Delivery used the global `fetch` with no address check, so an endpoint could point at the server itself or a cloud metadata address | high | Fixed: a `webhook` address policy refuses loopback, link-local, unspecified, reserved, 6to4, Teredo, documentation and IPv4-mapped forms, and is checked at save time and again on every connection inside the socket's lookup. Private ranges stay allowed, because self-hosted receivers live there (D20) | `tests/integration/webhooks/destination.test.ts`, `src/server/net/safe-fetch.test.ts` |
| Security headers | `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, CSP, HSTS on pages, API responses and the health endpoint | No response carried any of them. The sign-up page's `no-referrer` rule had to stay in force | medium | Fixed: static headers in `next.config.ts` with the sign-up rule last; a per-request CSP nonce and HSTS (https only) from the proxy; the root layout renders per request so scripts carry the nonce (D16, D17) | `tests/integration/security/headers.test.ts`, `src/lib/http/security-headers.test.ts` |
| Request size | Bodies without a declared length on the API and compose-check | The API buffered the whole body before measuring it, so a chunked body of any size was read into memory | medium | Fixed: `readBodyWithin` cancels the stream as soon as the limit is crossed. API limits are unchanged; compose-check is limited to 256 KB (D19) | `tests/integration/security/body-limit.test.ts`, `src/server/http/body.test.ts` |
| Server action body size | Next's `serverActions.bodySizeLimit` | Server actions accept up to 26 MB | low | Accepted: uploads need it. Every action requires a session and a role, and the proxy refuses cross-origin posts first | `tests/integration/security/csrf.test.ts` |
| Outbound fetches | Media by URL: ranges, redirects and DNS changes | The refused-address list missed 6to4, Teredo, documentation ranges and IPv4-compatible forms; mapped forms were judged as a whole rather than by the IPv4 address inside | medium | Fixed: the list is extended and mapped or compatible forms are judged by the address they carry. Redirects (at most 3) are re-checked on every hop, and the address is checked inside the socket's lookup on every connection | `src/server/net/safe-fetch.test.ts` |
| Session token in auth responses | Where the real session token appears in the scanned run | Besides its `Set-Cookie`, Better Auth returns the token in the JSON of `POST /api/auth/sign-in/email` (`token`) and `GET /api/auth/get-session` (`session.token`). Only the caller that holds the cookie receives it, but page script can read it there, which `HttpOnly` alone would prevent | low | Accepted: this is Better Auth's response contract (`node_modules/better-auth/dist/api/routes/sign-in.mjs`), the same party already holds the cookie, and the per-request CSP nonce limits injected script. Stripping the fields would need a response-rewriting hook on the auth handler; left as a later decision. The scan asserts both fields and scans everything else | `tests/integration/security/secret-scan.test.ts` |
| Session cookie attributes | `HttpOnly`, `SameSite`, `Secure` and the `__Secure-` prefix on http and https public URLs | None missing | none | Accepted: nothing found | `tests/integration/security/cookies.test.ts` |
| Sign-in rate limits | Limits per email and per IP | Four attempts for one email in ten seconds are refused with 429 whatever client address they claim. The per-IP rule is a loose backstop only, because the address can be client-chosen | none | Accepted: nothing found. Behind a proxy the trusted-header settings must match it (see the deployment guide) | `tests/integration/security/cookies.test.ts`, `tests/integration/auth-endpoints.test.ts` |
